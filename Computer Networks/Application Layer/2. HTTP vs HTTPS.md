# HTTP vs HTTPS

## What is HTTP?

**Definition:**  
**HTTP (HyperText Transfer Protocol)** is an **application-layer protocol** used for transmitting hypermedia documents (HTML, images, videos) between a **web client (browser)** and a **web server**.

It follows a **request-response model** — the client sends a request and the server returns a response.

**Port:** **80**  
**Layer:** Application Layer (Layer 7)  
**Transport:** TCP  
**State:** Stateless — each request is independent; the server retains no memory of previous requests.

---

## 1. How HTTP Works

![HTTP Working](images/http_working.gif)

**Steps:**
1. Client opens a TCP connection to the server on port 80.

2. Client sends an HTTP request (method, URL, headers, optional body).

3. Server processes the request and sends back an HTTP response (status code, headers, body).

4. Connection may be closed or kept alive for further requests.

---

## 2. HTTP Request Structure

```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Language: en-US
Connection: keep-alive
```

### Request Components

| Component | Description |
|-----------|-------------|
| **Request Line** | Method + URL path + HTTP version |
| **Headers** | Metadata — Host, User-Agent, Accept, Cookie, etc. |
| **Blank Line** | Separates headers from body |
| **Body** | Optional; used in POST/PUT requests to send data |

---

## 3. HTTP Methods

| Method | Description | Request Body | Idempotent | Safe |
|--------|-------------|-------------|-----------|------|
| **GET** | Retrieve a resource | No | Yes | Yes |
| **POST** | Submit data to create/process a resource | Yes | No | No |
| **PUT** | Replace a resource at the specified URL | Yes | Yes | No |
| **PATCH** | Partially update a resource | Yes | No | No |
| **DELETE** | Remove a resource | Optional | Yes | No |
| **HEAD** | Same as GET but returns only headers | No | Yes | Yes |
| **OPTIONS** | Describes the communication options for a resource | No | Yes | Yes |

**Idempotent:** Repeating the same request produces the same result.  
**Safe:** The request does not modify server state.

---

## 4. HTTP Response Structure

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 3056
Cache-Control: max-age=3600
Connection: keep-alive

<!DOCTYPE html>
<html>...
```

### Response Components

| Component | Description |
|-----------|-------------|
| **Status Line** | HTTP version + status code + reason phrase |
| **Headers** | Metadata — Content-Type, Content-Length, Set-Cookie, etc. |
| **Blank Line** | Separates headers from body |
| **Body** | The actual content (HTML, JSON, image bytes, etc.) |

---

## 5. HTTP Status Codes

Status codes are grouped into 5 classes:

| Class | Range | Meaning |
|-------|-------|---------|
| **1xx** | 100–199 | Informational — request received, processing continues |
| **2xx** | 200–299 | Success — request successfully received and processed |
| **3xx** | 300–399 | Redirection — further action needed |
| **4xx** | 400–499 | Client Error — client-side problem |
| **5xx** | 500–599 | Server Error — server-side problem |

### Commonly Tested Status Codes

| Code | Text | Description |
|------|------|-------------|
| **200** | OK | Request succeeded; body contains the resource |
| **201** | Created | Resource successfully created (used with POST/PUT) |
| **204** | No Content | Success; no body in response (used with DELETE) |
| **301** | Moved Permanently | Resource has permanently moved to a new URL |
| **302** | Found | Temporary redirect to another URL |
| **304** | Not Modified | Cached version is still valid; no body returned |
| **400** | Bad Request | Malformed or invalid request syntax |
| **401** | Unauthorized | Authentication required |
| **403** | Forbidden | Authenticated but not authorised |
| **404** | Not Found | Resource does not exist |
| **405** | Method Not Allowed | HTTP method not supported by this endpoint |
| **408** | Request Timeout | Server timed out waiting for the request |
| **429** | Too Many Requests | Rate limit exceeded |
| **500** | Internal Server Error | Generic server-side error |
| **502** | Bad Gateway | Server received invalid response from upstream |
| **503** | Service Unavailable | Server temporarily unable to handle requests |
| **504** | Gateway Timeout | Upstream server did not respond in time |

## 6. HTTP Versions

| Version | Year | Key Features |
|---------|------|-------------|
| **HTTP/0.9** | 1991 | Single-line protocol; GET only; no headers |
| **HTTP/1.0** | 1996 | Headers, status codes, methods; new TCP connection per request |
| **HTTP/1.1** | 1997 | Persistent connections (`keep-alive`), pipelining, chunked transfer, virtual hosting |
| **HTTP/2** | 2015 | Binary framing, multiplexing (many requests over one connection), header compression (HPACK), server push |
| **HTTP/3** | 2022 | Built on **QUIC** (UDP), eliminates head-of-line blocking, 0-RTT connection setup, always encrypted |

**HTTP/1.1 vs HTTP/2 — Key Improvement:**  
HTTP/1.1 suffers from **Head-of-Line (HoL) blocking** — responses must be received in order even over persistent connections. HTTP/2 uses **multiplexed streams**, allowing multiple interleaved responses on one TCP connection.

## 7. What is HTTPS?

**Definition:**  
**HTTPS (HyperText Transfer Protocol Secure)** is **HTTP with an added layer of security** provided by **TLS (Transport Layer Security)** — formerly SSL.

HTTPS ensures:
- **Confidentiality:** Data is encrypted; cannot be read by eavesdroppers.
- **Integrity:** Data cannot be tampered with in transit.
- **Authentication:** The server's identity is verified using a digital certificate.

**Port:** **443**  
**Transport:** TCP + TLS  

---

## 8. How HTTPS Works — TLS Handshake

Before HTTP data flows, a **TLS handshake** establishes an encrypted channel:

![HTTPS Working](images/https_working.gif)

### TLS Certificate

A **TLS Certificate** is a digital document issued by a trusted **Certificate Authority (CA)** (e.g., Let's Encrypt, DigiCert, GlobalSign) that:
- Proves the server owns the domain.
- Contains the server's **public key** used in the handshake.
- Is signed by the CA's private key, allowing browsers to verify it.

### Certificate Verification Steps

1. Browser checks the certificate's **domain name** matches the site.
2. Browser verifies the **certificate chain** up to a trusted Root CA.
3. Browser checks the certificate has **not expired**.
4. Browser checks the certificate has **not been revoked** (via CRL or OCSP).

---

## 9. HTTP vs HTTPS — Full Comparison

| Feature | HTTP | HTTPS |
|---------|------|-------|
| **Full Name** | HyperText Transfer Protocol | HyperText Transfer Protocol Secure |
| **Port** | 80 | 443 |
| **Security** | No encryption | Encrypted via TLS |
| **Authentication** | None | Server verified by digital certificate |
| **Data Integrity** | Not guaranteed | Guaranteed (TLS) |
| **Speed** | Slightly faster (no handshake) | Marginally slower (handshake overhead) |
| **SEO** | Lower search ranking | Preferred by Google (ranking boost) |
| **Browser Indicator** | "Not Secure" warning | Padlock icon |
| **Certificate Required** | No | Yes (from trusted CA) |
| **Use Case** | Internal/testing environments | All production websites |
| **HTTP Version** | Up to HTTP/1.1 without HTTPS | HTTP/2 and HTTP/3 require TLS |

---

## 10. HTTP Cookies and Sessions

Since HTTP is **stateless**, cookies are used to maintain state across multiple requests.

**Cookie Lifecycle:**
1. Server sends `Set-Cookie` header in a response.
2. Browser stores the cookie and includes it in all subsequent requests to that domain.
3. Server reads the cookie to identify the session or user.

| Cookie Attribute | Description |
|------------------|-------------|
| **HttpOnly** | Cookie cannot be accessed by JavaScript (prevents XSS theft) |
| **Secure** | Cookie only sent over HTTPS connections |
| **SameSite** | Controls cross-site cookie sending (prevents CSRF) |
| **Expires / Max-Age** | Sets the cookie lifetime |

---

## Summary

- **HTTP** is a stateless protocol for transferring hypermedia documents.

- **HTTPS** adds security via TLS, ensuring confidentiality, integrity, and authentication.

- HTTP/2 and HTTP/3 improve performance with multiplexing and QUIC, but require HTTPS.

- Understanding HTTP methods, status codes, headers, and the TLS handshake is crucial
