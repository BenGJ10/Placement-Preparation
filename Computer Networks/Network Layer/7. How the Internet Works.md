# How the Internet Works

This document traces the complete journey of a network request — from the moment a user types a URL into a browser to the moment a web page is rendered on screen. Every step maps to a specific layer of the OSI/TCP-IP model and a specific protocol.

This is one of the most commonly asked interview questions in systems and networking:

> "What happens when you type `https://www.google.com` and press Enter?"

---

## Overview: The Big Picture

```
User types URL
      ↓
Browser parses URL
      ↓
DNS Resolution (URL → IP Address)
      ↓
TCP Connection Established (3-Way Handshake)
      ↓
TLS Handshake (for HTTPS)
      ↓
HTTP Request sent
      ↓
Server processes and sends HTTP Response
      ↓
Browser renders the page
      ↓
TCP Connection Closed
```

Each of these steps involves multiple layers of the networking stack working together.

---

## Step 1: You Type the URL

You enter `https://www.google.com` in the browser and press Enter.

### Browser Parses the URL

The browser immediately breaks the URL into components:

| Component  | Value            | Meaning                                    |
|------------|------------------|--------------------------------------------|
| **Scheme** | `https`          | Use HTTPS (HTTP over TLS/SSL)              |
| **Host**   | `www.google.com` | The server to contact                      |
| **Path**   | `/`              | Root resource on the server                |
| **Port**   | `443` (implied)  | Default port for HTTPS (80 for HTTP)       |

### Browser Cache Check

Before making any network request, the browser checks its own cache:

1. **Browser DNS cache** — has this domain been resolved recently?
2. **Browser HTTP cache** — is there a cached response that is still valid (based on `Cache-Control` or `Expires` headers)?

If a valid cache entry exists, the browser uses it and skips many of the following steps.

---

## Step 2: DNS Resolution

The browser needs to know the **IP address** of `www.google.com` before it can connect. This is the job of **DNS (Domain Name System)**.

### DNS Cache Hierarchy

Resolution is attempted at each level before escalating:

```
Browser Cache → OS Cache → Router Cache → Recursive Resolver → Root NS → TLD NS → Authoritative NS
```

### Full DNS Resolution Process

**1. OS Cache Check**

The browser asks the operating system. The OS checks `/etc/hosts` (Linux/Mac) or `C:\Windows\System32\drivers\etc\hosts` (Windows) first, then its own DNS cache.

**2. Recursive Resolver (ISP or Public DNS)**

If the OS cache misses, it queries the configured **Recursive DNS Resolver** (e.g., `8.8.8.8` for Google DNS, `1.1.1.1` for Cloudflare, or the ISP's resolver).

The resolver takes over and queries on behalf of the client.

**3. Root Name Server**

The resolver contacts one of the 13 **Root Name Server** clusters (managed by IANA/ICANN).

The Root NS does not know `www.google.com` but knows where to find `.com` domains:

```
Query:  "Who handles .com?"
Reply:  "Ask the .com TLD Name Server at <IP>"
```

**4. TLD Name Server**

The resolver queries the `.com` **Top-Level Domain (TLD) Name Server**.

```
Query:  "Who handles google.com?"
Reply:  "Ask Google's Authoritative Name Server at <IP>"
```

**5. Authoritative Name Server**

The resolver queries Google's own **Authoritative Name Server**.

```
Query:  "What is the IP address of www.google.com?"
Reply:  "142.250.192.46" (example)
```

The resolver returns the IP to the OS, which passes it to the browser. Both cache the result with the record's **TTL (Time To Live)** value.

### DNS Record Types

| Record | Purpose                                       |
|--------|-----------------------------------------------|
| **A**  | Maps domain to IPv4 address                   |
| **AAAA** | Maps domain to IPv6 address                 |
| **CNAME** | Canonical Name — alias for another domain  |
| **MX** | Mail Exchange — specifies mail servers        |
| **NS** | Name Server — delegates DNS authority         |
| **TXT** | Arbitrary text — used for SPF, DKIM, verification |
| **PTR** | Reverse DNS — IP address to domain name      |

### DNS Transport

- DNS queries typically use **UDP port 53** (fast, connectionless)
- If the response exceeds 512 bytes, **TCP port 53** is used (reliable, larger payloads)
- **DNS over HTTPS (DoH)** and **DNS over TLS (DoT)** are modern encrypted alternatives

## Step 3: Establishing a TCP Connection — 3-Way Handshake

Now that the browser has the IP address (`142.250.192.46`), it initiates a **TCP connection** to port `443`.

TCP is a **connection-oriented** protocol — a connection must be established before any data is exchanged.

### The 3-Way Handshake

```
    Client                           Server
      |                                 |
      |------- SYN (seq=x) ------------>|
      |                                 |
      |<------ SYN-ACK (seq=y, ack=x+1) |
      |                                 |
      |------- ACK (ack=y+1) ---------->|
      |                                 |
      |  [Connection Established]       |
```


| Step | Packet       | Meaning                                                 |
|------|--------------|---------------------------------------------------------|
| 1    | **SYN**      | Client: "I want to connect, my sequence number starts at x" |
| 2    | **SYN-ACK**  | Server: "Accepted, my sequence is y, acknowledging x+1" |
| 3    | **ACK**      | Client: "Confirmed, acknowledging y+1"                  |

After the handshake, both sides have:
- Agreed on initial sequence numbers
- Synchronized TCP state
- An established, bidirectional connection

### What Happens at Each Layer During Connection

| OSI Layer        | Activity                                                       |
|------------------|----------------------------------------------------------------|
| **Application**  | Browser prepares HTTPS request                                 |
| **Transport**    | TCP creates segments, assigns ports (client: ephemeral, server: 443) |
| **Network**      | IP adds source and destination IP addresses                    |
| **Data Link**    | Ethernet frame created with MAC addresses (ARP resolves gateway MAC) |
| **Physical**     | Bits transmitted over the wire/wireless medium                 |

---

## Step 4: TLS Handshake (HTTPS Security)

Since the scheme is `https`, a **TLS (Transport Layer Security) handshake** occurs immediately after the TCP connection is established.

TLS provides:
- **Confidentiality** — data is encrypted
- **Integrity** — data cannot be tampered with
- **Authentication** — the server's identity is verified using certificates

### TLS 1.3 Handshake (Simplified)

```
    Client                           Server
      |                                 |
      |------- ClientHello ------------>|
      |                                 |
      |<------ ServerHello -------------|
      |<------ Certificate -------------|
      |<------ ServerHelloDone ---------|
      |                                 |
      |------- ClientKeyExchange ------>|
      |------- ChangeCipherSpec ------->|
      |------- Finished --------------->|
      |                                 |
      |<------ ChangeCipherSpec --------|
      |<------ Finished ----------------|
      |                                 |
      | [Secure Connection Established] |
```

### Certificate Verification

The server presents a **TLS Certificate** containing:
- Domain name (Common Name / Subject Alternative Name)
- Public key
- Certificate Authority (CA) signature
- Validity period

The browser verifies:
1. The certificate is signed by a trusted **Certificate Authority (CA)** (e.g., DigiCert, Let's Encrypt)
2. The certificate covers the requested domain
3. The certificate has not expired
4. The certificate has not been revoked (via CRL or OCSP)

After verification, symmetric session keys are derived using the exchanged key material, and all subsequent communication is **encrypted**.

---

## Step 5: HTTP Request

With the encrypted channel in place, the browser sends an **HTTP GET request**:

```
GET / HTTP/1.1
Host: www.google.com
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml,...
Accept-Language: en-US,en;q=0.9
Accept-Encoding: gzip, deflate, br
Connection: keep-alive
Cookie: <session cookies if any>
```

### Key HTTP Request Fields

| Header           | Purpose                                                   |
|------------------|-----------------------------------------------------------|
| `GET /`          | Request the root resource using the GET method           |
| `Host`           | Required in HTTP/1.1; specifies the target domain        |
| `User-Agent`     | Browser and OS identification                            |
| `Accept`         | Content types the client can handle                      |
| `Accept-Encoding`| Compression formats supported (gzip, brotli)            |
| `Connection`     | `keep-alive` reuses the TCP connection for multiple requests |
| `Cookie`         | Session data for authentication/personalization          |

---

## Step 6: Data Travels Through the Network

The HTTP request is now a stream of bytes. Here is what happens as it traverses the internet:

### Encapsulation (Sender Side — Going Down the Stack)

| Layer            | Unit     | What is Added                                      |
|------------------|----------|----------------------------------------------------|
| **Application**  | Data     | HTTP request payload                               |
| **Transport**    | Segment  | TCP header (source/dest port, seq number, checksum)|
| **Network**      | Packet   | IP header (source/dest IP, TTL, protocol)          |
| **Data Link**    | Frame    | Ethernet header (MAC addresses), trailer (CRC)     |
| **Physical**     | Bits     | Electrical/optical/radio signals                   |

### Routing Through the Internet

1. The frame is sent to the **default gateway** (home/office router).
2. The router strips the Ethernet frame, reads the IP destination, and looks up its **routing table**.
3. The packet is forwarded hop-by-hop through **ISP routers**, **backbone routers**, and **data center routers**.
4. Each router decrements the **TTL** by 1. If TTL reaches 0, the packet is dropped and an **ICMP Time Exceeded** message is sent back.
5. **BGP** is used by backbone routers to determine the best inter-AS path.
6. **OSPF or IS-IS** is used within each AS for intra-domain routing.

### At Each Router

```
Receive frame → Strip L2 header → Read destination IP
      ↓
Look up routing table (longest prefix match)
      ↓
Determine next hop → Apply new L2 header (ARP resolves next-hop MAC)
      ↓
Forward out the appropriate interface
```


### Decapsulation (Receiver Side — Going Up the Stack)

At the destination server, the process is reversed:

| Layer            | Action                                                |
|------------------|-------------------------------------------------------|
| **Physical**     | Bits received and converted to frame                 |
| **Data Link**    | MAC address verified; Ethernet header stripped       |
| **Network**      | IP header processed; packet delivered to transport   |
| **Transport**    | TCP header processed; data ordered and reassembled   |
| **Application**  | HTTP request received and processed by web server    |

---

## Step 7: Server Processes the Request

The web server (e.g., Nginx, Apache) receives the HTTP request and:

1. **Parses the request** — method, path, headers
2. **Authentication / Session check** — validates cookies or tokens if required
3. **Application logic** — queries databases, calls microservices, executes backend code
4. **Constructs the HTTP response** — HTML content, status code, headers

### HTTP Response

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Encoding: gzip
Content-Length: 12345
Cache-Control: private, max-age=0
Set-Cookie: session=abc123; Secure; HttpOnly
Date: Tue, 01 Apr 2026 09:00:00 GMT

<!DOCTYPE html>
<html>...
```

### Common HTTP Status Codes

| Code | Meaning                              |
|------|--------------------------------------|
| 200  | OK — Request succeeded               |
| 301  | Moved Permanently — Redirect         |
| 302  | Found — Temporary redirect           |
| 304  | Not Modified — Use cached version    |
| 400  | Bad Request — Malformed request      |
| 401  | Unauthorized — Authentication needed|
| 403  | Forbidden — Access denied            |
| 404  | Not Found — Resource does not exist  |
| 500  | Internal Server Error                |
| 503  | Service Unavailable                  |

---

## Step 8: Browser Renders the Page

The browser receives the HTTP response and begins rendering:

1. **Parse HTML** → Build **DOM (Document Object Model)** tree
2. **Parse CSS** → Build **CSSOM (CSS Object Model)** tree
3. **Combine DOM + CSSOM** → **Render Tree**
4. **Layout** → Calculate position and size of each element
5. **Paint** → Draw pixels on screen
6. **Composite** → Layer composition for final display

### Sub-resource Requests

While parsing the HTML, the browser encounters additional resources:
- **CSS files** — fetched and parsed
- **JavaScript files** — fetched, parsed, and executed
- **Images** — fetched asynchronously
- **Fonts** — fetched as referenced

Each sub-resource triggers its own DNS + TCP (or reused connection) + HTTP cycle. Modern browsers use:
- **HTTP/2 multiplexing** — multiple requests over a single TCP connection
- **HTTP/3 (QUIC)** — HTTP over UDP for lower latency
- **Connection reuse** — `keep-alive` avoids repeated handshakes

---

## Step 9: TCP Connection Teardown

Once all resources are loaded (or after a timeout), the TCP connection is closed gracefully using a **4-step teardown**:

```
Client                          Server
  |                               |
  |------- FIN ------------------>|   Client: "I'm done sending"
  |<------ ACK -------------------|   Server: "Acknowledged"
  |<------ FIN -------------------|   Server: "I'm done too"
  |------- ACK ------------------>|   Client: "Acknowledged"
  |                               |
  |     [Connection Closed]       |
```

The connection enters a **TIME_WAIT** state on the client side for 2× MSL (Maximum Segment Lifetime, typically 2 minutes) to ensure all packets are received and prevent old packets from interfering with new connections.

## Complete Protocol Stack Summary

| Step                             | Protocols Involved                              | OSI Layer(s)         |
|----------------------------------|-------------------------------------------------|----------------------|
| URL parsing                      | Browser internals                               | Application          |
| DNS resolution                   | DNS (UDP/TCP port 53)                           | Application          |
| TCP connection                   | TCP (3-way handshake)                           | Transport            |
| TLS handshake                    | TLS 1.3, X.509 certificates, PKI               | Session/Presentation |
| HTTP request/response            | HTTP/1.1, HTTP/2, HTTP/3                        | Application          |
| IP routing                       | IP, BGP, OSPF, ARP, ICMP                        | Network              |
| Frame delivery                   | Ethernet, Wi-Fi (802.11)                        | Data Link            |
| Signal transmission              | Fiber optics, copper, radio waves               | Physical             |
| Connection teardown              | TCP (4-step FIN)                                | Transport            |

## Key Takeaways

- DNS resolution converts a domain name to an IP address through a hierarchy of servers — browser cache → OS → recursive resolver → root → TLD → authoritative.

- A TCP 3-way handshake (SYN, SYN-ACK, ACK) establishes a reliable connection before any data is sent.

- TLS adds encryption, authentication, and integrity verification on top of TCP for HTTPS.

- IP routing forwards packets hop-by-hop across the internet using longest-prefix-match; BGP is used between ISPs and OSPF within them.

- ARP is used at each hop to resolve the next-hop router's MAC address before framing.

- NAT rewrites the source IP from private to public as packets leave the local network.

- HTTP requests and responses carry the actual web content; TCP handles reliability and ordering.

- TCP teardown uses a 4-step FIN sequence; TIME_WAIT ensures clean connection closure.

- Modern browsers optimize using HTTP/2 multiplexing, connection reuse, DNS prefetching, and CDN caching.
