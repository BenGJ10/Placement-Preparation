# Page Fault Handling

**Page Fault Handling** is the core mechanism that makes demand paging work, enabling virtual memory systems to transparently move data between RAM and disk.

Understanding the page fault handling sequence is critical for OS exams and interviews.

---

## 1. What is a Page Fault?

### Definition

A **page fault** occurs when:
> A process accesses a virtual address whose **corresponding page is NOT currently in physical memory**.

### Trigger

When MMU tries to translate a virtual address and finds:
- **Valid bit = 0** in page table entry
- Page flagged as "not in memory"

### Result

CPU raises an **exception/interrupt**, suspending normal execution.

---

## 2. Types of Page Faults

### Valid Page Fault

- Page **belongs to process** (in page table)
- Page **not currently in RAM**
- Page **stored on disk**
- **Action:** Fetch from disk and load

**Example:** First access to a memory region

### Invalid Page Fault

- Address **outside process address space**
- **No page table entry** for address
- **Action:** Terminate process (segmentation fault)

**Example:** Access beyond stack limit, unallocated heap

---

## 3. Page Fault Exception

### How It Occurs

```
Process generates logical address
              ↓
MMU translates (page table lookup)
              ↓
Valid bit = 0 ?
     YES ↓
Exception raised (INT14 on x86)
              ↓
Control passes to OS page fault handler
              ↓
Kernel mode execution
```

---

## 4. Page Fault Handler (Kernel Code)

### High-Level Steps

```
Page_Fault_Handler:
  1. Validate the address (is it legitimate?)
  2. Find/allocate a free frame in RAM
  3. Schedule disk I/O to fetch the page
  4. Wait for I/O completion
  5. Update page table entry
  6. Restore process context
  7. Return from interrupt
  8. Process retries the faulting instruction
```

---

## 5. Detailed Page Fault Handling Sequence

### Step 1: Determine Fault Validity

```
IF address outside page table range
  THEN page_not_belong_to_process
       SIGNAL(SIGSEGV)  // Segmentation violation
       TERMINATE process
       RETURN

IF address within range
  AND valid bit already set
  AND no protection violation
  THEN Page is in memory (not a valid fault)
       RETURN (should not happen)

ELSE Page is in disk
  PROCEED to Step 2
```

### Step 2: Check for Free Frame

```
Look for free frame in frame table

IF free frame available
  THEN Allocate it
       PROCEED to Step 3

ELSE No free frame
  THEN SELECT victim page (page replacement)
       IF victim is dirty
         THEN Write victim to disk
       MARK victim's page table invalid
       FREE the frame
       ALLOCATE frame for faulting page
       PROCEED to Step 3
```

### Step 3: Issue Disk I/O Request

```
Queue disk request:
  - Read page from disk swap space
  - Target frame in physical RAM
  - Upon completion, interrupt CPU

Context switch to another ready process
(faulting process blocked waiting for I/O)
```

### Step 4: I/O Completion

```
Disk I/O completes (10-100 ms later)
              ↓
Interrupt raised
              ↓
Page now in RAM (frame allocated)
```

### Step 5: Update Page Table

```
Page_Table[page_number].frame = allocated_frame_number
Page_Table[page_number].valid_bit = 1
Page_Table[page_number].reference_bit = 1
(other bits set as needed)
```

### Step 6: Ready Process

```
Faulting process moved from
  Waiting queue → Ready queue

Waiting for CPU scheduling
```

### Step 7: Resume Execution

```
When process scheduled to run again:
  RESTORE CPU registers
  RESTORE program counter (to faulting instruction)
  RETURN from interrupt
  RETRY the instruction that caused fault
  (Now page is in memory, translation succeeds)
```

## 6. Visual Page Fault Timeline

```
Time  Event
-----|------------------------------------------------------------
0     Process P1 running
      Accesses address → page fault
      
1     CPU raises exception
      Saves state, transfers to OS
      
2     Page fault handler validates address
      Checks if page belongs to process
      
3     Page replacement algorithm selects victim
      Dirty bit check
      Write victim to disk if needed
      
4     I/O request issued to disk controller
      P1 moved to waiting queue
      
5     CPU context switched to another process
      Other processes run while disk I/O happens
      
6-100 Disk I/O in progress (10-100 ms typical)
      
101   Disk I/O completes
      Interrupt raised
      Page in RAM, page table updated
      P1 moved to ready queue
      
102   Scheduler selects P1
      CPU registers restored
      Return from interrupt
      
103   Process retries faulting instruction
      Translation now succeeds
      Execution continues normally
```

## 7. Page Replacement During Fault

### When Needed

If no free frames available:

```
Victim selection (page replacement algorithm)
           ↓
         [LRU, FIFO, Optimal, etc.]
           ↓
Victim page evicted from RAM
           ↓
If modified (dirty bit = 1):
    Write to disk first
           ↓
Frame now available for faulting page
```

### Common Algorithms

| Algorithm | Criterion | Performance |
|-----------|-----------|-------------|
| **FIFO** | First page in, first out | Poor |
| **LRU** | Least Recently Used | Good |
| **LFU** | Least Frequently Used | Good |
| **Optimal** | Theoretically best (predict future) | Impossible |
| **Clock** | Circular buffer with reference bits | Practical |

## 8. Cost Analysis

### Page Fault Cost Components

```
Total Cost = 
  Context switch overhead (1-10 μs) +
  I/O setup overhead (1-5 μs) +
  Disk I/O time (10-100 ms) +
  I/O completion handling (1-5 μs) +
  Context switch back (1-10 μs)
  ≈ 10-100 ms dominated by disk I/O
```

### Impact on Memory Access Time

Without faults:
- Typical access: ~100 ns

With 0.1% fault rate:
- Effective time: 0.999 × 100 + 0.001 × 10,000,000 ≈ 10,000 ns
- **100× slowdown**

**Critical:** Minimize fault rate via good locality

## 9. Copy-on-Write (Optimization)

### Scenario: Process Fork

Normally:
- Copy entire address space (expensive)

Optimization:
```
Fork request
    ↓
Share all pages (both processes)
Mark pages "copy-on-write"
    ↓
If child/parent modifies page:
  Page fault on write
    ↓
  OS creates copy
    ↓
  Continue with separate page
```

**Benefit:** Fork very cheap if child doesn't modify memory

## 10. Major Page Fault vs Minor Page Fault

### Minor Page Fault

- Page already in RAM
- Just not mapped to process
- Very fast (update page table only)

**Example:** Shared library first access

### Major Page Fault

- Page on disk
- Requires disk I/O
- Very slow (10-100 ms)

**Example:** First access to large data structure

---

## 11. Error Handling

### Access Violations During Fault

```
IF page fault on invalid address:
  SIGNAL segmentation fault
  TERMINATE process
  
IF page fault but permission denied:
  SIGNAL permission fault
  TERMINATE process
  
IF page fault on COW (copy-on-write):
  Create copy, retry

IF page fault on stack guard:
  Stack overflow detected
  TERMINATE process
```

## 12. Real-World Analogy

**Librarian page fault handling**

1. Student asks for book (page fault)
2. Librarian checks if request legitimate
3. Checks shelf (RAM) for book
4. Not on shelf → Request from warehouse (disk)
5. Book arrives from warehouse (I/O complete)
6. Place on shelf (update page table)
7. Student gets book (process resumes)

## 13. Page Fault Handling Best Practices

### For Systems

- **Minimize fault frequency** via good page replacement
- **Fast fault handler** (keep in fast code paths)
- **Effective TLB** to reduce translation overhead
- **Monitor fault rate** as performance metric

### For Applications

- **Access data sequentially** (improve locality)
- **Minimize working set** (keep active data small)
- **Avoid thrashing** (repeatedly faulting on same pages)
- **Understand page size** (usually 4 KB on x86)

## 14. Linux Page Fault Handler Flow

```
Fault at address X
    ↓
do_page_fault()
    ├→ Validate address (within VMA)
    ├→ Check permissions
    ├→ Handle special cases (COW, swapped)
    ├→ Handle_mm_fault()
    │  ├→ Allocate page from memory
    │  ├→ Fetch from disk if needed
    │  └→ Update page table
    └→ Return & retry instruction
```

| Phase | Action | Duration |
|-------|--------|----------|
| Exception | Raise, context save | ~1 μs |
| Validation | Check address legitimacy | ~1 μs |
| Replacement | Evict victim if needed | ~1 μs |
| I/O | Fetch from disk | 10-100 ms |
| Completion | Update tables, ready process | ~1 μs |
| Resume | Retry instruction | ~1 μs |
| **Total** | | **10-100 ms** |

## Key Takeaways

- **Page fault** interrupts execution when page not in RAM.

- **Handler validates** address, allocates frame, issues disk I/O.

- **Process blocked** during fault, others run (if available).

- **Fault cost ~10-100 ms** (dominated by disk I/O).

- **Page replacement** needed if no free frame available.

- **Locality essential** to minimize fault frequency.

- Interview focus: **fault sequence, replacement strategies, optimization techniques, performance impact**.
