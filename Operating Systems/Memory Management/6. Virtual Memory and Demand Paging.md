# Virtual Memory and Demand Paging

**Virtual Memory** and **Demand Paging** are revolutionary concepts that allow processes to run even when they exceed physical RAM size, enabling efficient multitasking and illusion of unlimited memory.

These concepts are critical for interviews and understanding modern OS design.

---

## 1. What is Virtual Memory?

### Definition

**Virtual Memory** is an abstraction that presents each process with a **uniform, contiguous memory space** that can be **larger than physical RAM**.

The OS manages mapping between virtual and physical memory, transparently bringing data from disk as needed.

---

## 2. Why Virtual Memory is Needed

### Limitations Without Virtual Memory

- Process size limited to physical RAM
- Only as many processes as RAM can hold
- Inefficient memory utilization
- No protection between processes

### Solutions Virtual Memory Provides

- Processes can be **larger than RAM**
- **Higher degree of multiprogramming**
- Process isolation and protection
- Efficient memory utilization
- Transparent data movement

---

## 3. Virtual Memory Architecture

### Components

```
Virtual Address Space (Process view)
    ↓
[Page Table / Segment Table]
    ↓
Physical RAM (limited size)
    ↓
Secondary Storage (Disk)
```

### Key Concept

- Process sees virtual addresses (logical space)
- OS maps virtual → physical via page/segment table
- Not all virtual memory needs to be in RAM at once
- OS brings pages from disk on demand

---

## 4. Virtual Address Space

### Definition

The **logical memory space** visible to a process.

### Characteristics

- Usually much larger than physical RAM
- Starts at address 0 for each process
- Protected from other processes
- Process unaware of actual RAM layout

### Example: 32-bit System

- Virtual address space: 2^32 = 4 GB per process
- Physical RAM: Maybe 8 GB (shared by all)
- Each process thinks it has 4 GB

---

## 5. Demand Paging

### Definition

**Demand Paging** brings a page into memory **only when requested** (when a page fault occurs), not all at process startup.

### Basic Principle

```
Process runs with some pages in RAM
        ↓
Requests address not in RAM
        ↓
Page Fault occurs
        ↓
OS fetches page from disk
        ↓
Adds to RAM, updates page table
        ↓
Process resumes
```

---

## 6. Page Fault

### Definition

A **page fault** occurs when a process accesses a page that is **not currently in physical memory**.

### When It Occurs

1. Process generates virtual address
2. MMU checks page table
3. Valid bit = 0 (page not in memory)
4. **Page fault exception** raised
5. OS interrupt handler invoked

### Page Fault Handler

```
Page Fault Handler:
  1. Find free frame in RAM
  2. Load page from disk into frame
  3. Update page table entry
  4. Set valid bit = 1
  5. Return from interrupt
  6. Process retries memory access
```

### Performance Impact

- **Page fault expensive** (disk I/O ~10-100 ms)
- Each fault causes system pause
- Careful page replacement strategy crucial
- **Locality principle** helps minimize faults

---

## 7. Advantages of Virtual Memory

✅ **Process Size Flexibility**
- Program can be larger than RAM
- Not limited by physical memory

✅ **Multiprogramming Efficiency**
- More processes in RAM
- Better CPU utilization

✅ **Protection and Isolation**
- Each process separate address space
- Cannot corrupt other process memory

✅ **Easy Relocation**
- Process can be placed anywhere in RAM
- Virtual addresses remain unchanged

✅ **Sharing**
- Pages/segments shared between processes
- Example: shared libraries in memory once

✅ **Simplified Memory Management**
- Logical view simpler than physical
- OS handles complexity

---

## 8. Disadvantages of Virtual Memory

❌ **Complexity**
- Complex translation mechanism
- Page table overhead

❌ **Performance Overhead**
- Translation delay (mitigated by TLB)
- Page faults very expensive

❌ **Thrashing Risk**
- Excessive page faults degrade performance
- Working set must fit in RAM

❌ **Disk I/O Bottleneck**
- Page faults cause disk I/O
- I/O can become system bottleneck

❌ **Swap Space Management**
- Extra disk space needed
- Must be carefully provisioned

---

## 9. Virtual Memory Performance Metrics

### Page Fault Rate

**Formula:**
```
Effective Memory Access Time = (1 - p) × Memory Access Time + p × Page Fault Time

Where:
p = page fault probability
Memory Access Time ≈ 100 ns
Page Fault Time ≈ 10-100 ms
```

**Example:**
```
If p = 0.001 (0.1% faults):
EMAT = 0.999 × 100 + 0.001 × 10,000,000
     = 100 + 10,000 = 10,100 ns
     ≈ 100x slowdown!
```

### Working Set

- Set of pages actively used by process
- Should fit in RAM to minimize faults
- Changes as program runs

### Locality

- **Temporal:** Recently used pages likely needed again
- **Spatial:** Adjacent pages likely needed together
- Drives effectiveness of paging

---

## 10. Demand Paging Implementation

### Steps in Lazy Loading

1. **Process creation:** Load only necessary pages (code start, stack)
2. **Execution:** As process runs, access new pages
3. **Page fault:** OS loads missing page
4. **Continue:** Process resumes from fault

### Copy-on-Write Optimization

When process created (fork):
- Share all pages initially
- Mark as "copy-on-write"
- If page modified, create copy
- Saves memory and time

## 11. Real-World Analogy

**Just-in-time book delivery service**

- Virtual memory = Library card (access to all books)
- Physical library = RAM
- Bookshelf = Page table
- Personal library = Loaded pages
- Requesting book = Page access
- Book not available = Page fault
- Delivery truck = Disk I/O
- Delivery time = Page fault time

## 12. Modern Systems and Virtual Memory

### Implementations

**Linux:**
- Demand paging with page-level granularity
- ~4 KB pages on x86
- Page faults handled by kernel

**Windows:**
- Demand paging with 4 KB pages
- Sophisticated page replacement
- Dynamic working set adjustment

**macOS:**
- Similar to Linux
- Memory compression instead of just swapping

---

## 13. Virtual Memory vs Physical Memory

| Aspect | Virtual Memory | Physical Memory |
|--------|----------------|-----------------|
| **Size** | Large (can be 4-64 GB) | Limited (actual RAM) |
| **Backing** | Mix of RAM + disk | Only RAM |
| **Process view** | One large continuous space | Fragmented view |
| **Translation** | Via page/segment table | Direct hardware access |
| **Access time** | Variable (100 ns to 100 ms) | Uniform (~100 ns) |

---

## 14. Page In vs Page Out

### Page In (Demand Paging)

```
Page fault → OS allocates frame → Reads from disk → Updates page table → Resumes
```

### Page Out (Eviction)

```
RAM full → Select victim page → Write to disk → Mark invalid → Free frame → Allocate to new page
```

**Trade-off:** Page out expensive if dirty bit set (modified data must be written)

## Summary

| Concept | Key Idea |
|---------|-----------|
| Virtual Memory | Memory abstraction larger than physical RAM |
| Demand Paging | Load pages only when needed |
| Page Fault | Exception when accessing non-resident page |
| Working Set | Active pages that should stay in RAM |
| Locality | Temporal and spatial usage patterns |

---

## Key Takeaways

- **Virtual Memory** allows processes larger than physical RAM.

- **Demand Paging** loads pages on-demand, not all upfront.

- **Page faults** expensive (10+ ms) but enable large processes.

- **Locality principle** ensures most accesses hit (low fault rate).

- **Working set** concept critical: must fit in RAM to avoid thrashing.

- **Trade-off:** Flexibility vs. potential performance hit.

- Interview questions focus on **page fault handling, virtual → physical translation, thrashing, and performance analysis**.
