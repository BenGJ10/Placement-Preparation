# SOLID Principles in Object-Oriented Design

**SOLID** is a set of **five design principles** that help developers build:

* Maintainable systems
* Scalable architectures
* Flexible and testable code

> **SOLID is not about syntax — it’s about design discipline.**

---

## 1. What Are SOLID Principles?

SOLID is an acronym:

| Letter | Principle                       |
| ------ | ------------------------------- |
| S      | Single Responsibility Principle |
| O      | Open–Closed Principle           |
| L      | Liskov Substitution Principle   |
| I      | Interface Segregation Principle |
| D      | Dependency Inversion Principle  |

---

## 2. Why SOLID Matters

Without SOLID:

* Code becomes rigid
* Small changes cause large breakages
* Classes grow uncontrollably
* Systems become hard to test and extend

With SOLID:

* Code is modular
* Changes are localized
* Systems evolve safely

---

## `S — Single Responsibility Principle (SRP)`

## 3. Definition

> **A class should have only one reason to change.**

A class should focus on **one responsibility**, not many.

---

## 4. SRP Violation Example

```cpp
class Report {
public:
    void generateReport() {}
    void saveToFile() {}
};
```

Problems:

* Business logic + persistence logic mixed
* Change in storage affects report generation

---

## 5. SRP-Compliant Design

```cpp
class Report {
public:
    void generateReport() {}
};

class ReportSaver {
public:
    void saveToFile(const Report& report) {}
};
```

✔ Clear separation of concerns
✔ Easier to modify and test

---

## `O — Open–Closed Principle (OCP)`


## 6. Definition

> **Software entities should be open for extension, but closed for modification.**

Add new behavior **without changing existing code**.

---

## 7. OCP Violation Example

```cpp
class AreaCalculator {
public:
    double area(int type) {
        if (type == 1) return 3.14 * r * r;
        if (type == 2) return l * b;
        return 0;
    }
};
```

Problems:

* Every new shape requires modifying this class

---

## 8. OCP-Compliant Design (Polymorphism)

```cpp
class Shape {
public:
    virtual double area() const = 0;
};

class Circle : public Shape {
public:
    double area() const override {
        return 3.14 * r * r;
    }
};

class Rectangle : public Shape {
public:
    double area() const override {
        return l * b;
    }
};
```

✔ New shapes = new classes
✔ Existing code untouched

---

## `L — Liskov Substitution Principle (LSP)`

## 9. Definition

> **Objects of a derived class must be substitutable for objects of the base class without breaking correctness.**

If `B` is a subclass of `A`, then `A*` should work with `B` objects safely.

---

## 10. LSP Violation Example

```cpp
class Bird {
public:
    virtual void fly() {}
};

class Penguin : public Bird {
public:
    void fly() override {
        throw logic_error("Can't fly");
    }
};
```

Problem:

* Penguin is not a valid substitute for Bird

---

## 11. LSP-Compliant Design

```cpp
class Bird {
};

class FlyingBird : public Bird {
public:
    virtual void fly() {}
};

class Penguin : public Bird {
};
```

✔ Behavior aligned with abstraction
✔ No unexpected failures

---

## `I — Interface Segregation Principle (ISP)`

## 12. Definition

> **Clients should not be forced to depend on interfaces they do not use.**

Large interfaces should be **split into smaller, specific ones**.

---

## 13. ISP Violation Example

```cpp
class Machine {
public:
    virtual void print() = 0;
    virtual void scan() = 0;
};
```

Problem:

* Printer-only devices must implement `scan()`

---

## 14. ISP-Compliant Design

```cpp
class Printer {
public:
    virtual void print() = 0;
};

class Scanner {
public:
    virtual void scan() = 0;
};
```

✔ Focused interfaces
✔ No unused methods

---

## `D — Dependency Inversion Principle (DIP)`


## 15. Definition

> **High-level modules should not depend on low-level modules.
> Both should depend on abstractions.**

---

## 16. DIP Violation Example

```cpp
class FileLogger {
public:
    void log() {}
};

class Application {
    FileLogger logger;
};
```

Problems:

* Application tightly coupled to FileLogger

---

## 17. DIP-Compliant Design

```cpp
class Logger {
public:
    virtual void log() = 0;
};

class FileLogger : public Logger {
public:
    void log() override {}
};

class Application {
    Logger* logger;
public:
    Application(Logger* logger) : logger(logger) {}
};
```

✔ Loose coupling
✔ Easy to swap implementations

---

## 18. SOLID Principles Working Together

| Principle | Focus                 |
| --------- | --------------------- |
| SRP       | Responsibility        |
| OCP       | Extensibility         |
| LSP       | Correctness           |
| ISP       | Interface design      |
| DIP       | Dependency management |

SOLID principles **reinforce each other**.

---

## 19. SOLID vs Overengineering

SOLID does **not** mean:

* Too many classes
* Complex hierarchies
* Abstract everything

Use SOLID:

* Where change is expected
* Where flexibility is required

---

## Summary Table

| Principle | Core Idea              |
| --------- | ---------------------- |
| SRP       | One responsibility     |
| OCP       | Extend, don’t modify   |
| LSP       | Safe substitution      |
| ISP       | Small interfaces       |
| DIP       | Depend on abstractions |

---

## Key Takeaways

* SOLID principles guide **clean OOP design**

* They reduce coupling and increase flexibility

* SRP is the foundation

* Polymorphism enables OCP and LSP

* Interfaces enable ISP and DIP

* Use SOLID **pragmatically**, not blindly
