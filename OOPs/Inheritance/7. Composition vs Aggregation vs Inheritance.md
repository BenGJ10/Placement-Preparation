# Composition vs Aggregation vs Inheritance

These three concepts define **how classes relate to each other** in object-oriented design.

They answer a fundamental design question:

> **Should I reuse code by inheriting, owning, or referencing another class?**

Understanding this distinction is **critical for correct system design**.

---

## 1. High-Level Comparison (Big Picture)

| Relationship | Type           | Meaning                                    |
| ------------ | -------------- | ------------------------------------------ |
| Inheritance  | Is-a           | One class is a specialized form of another |
| Composition  | Has-a (strong) | One class owns another                     |
| Aggregation  | Has-a (weak)   | One class uses another                     |

---

## 2. Inheritance

### Definition

**Inheritance** creates an **is-a relationship**, where a derived class:

* Inherits behavior and state
* Can override behavior
* Participates in polymorphism

```cpp
class Animal {
public:
    void eat() {}
};

class Dog : public Animal {
public:
    void bark() {}
};
```

✔ `Dog` **is an** `Animal`

---

### Characteristics

| Aspect              | Inheritance    |
| ------------------- | -------------- |
| Relationship        | Is-a           |
| Coupling            | Tight          |
| Reusability         | Via base class |
| Polymorphism        | ✔ Yes          |
| Lifetime dependency | Independent    |

---

### Pros

* Enables runtime polymorphism
* Promotes code reuse
* Natural for hierarchies

### Cons

* Tight coupling
* Fragile base class problem
* Hard to change later

---

## 3. Composition

### Definition

**Composition** represents a **strong has-a relationship**, where:

* One class **owns** another
* Owned object’s lifetime is **bound to the owner**
* Destruction of owner destroys the owned object

> **Composition implies ownership.**

---

### Example

```cpp
class Engine {
public:
    void start() {}
};

class Car {
private:
    Engine engine;   // Composition
public:
    void drive() {
        engine.start();
    }
};
```

✔ `Car` **has an** `Engine`
✔ Engine cannot exist without Car (in this design)

---

### Characteristics

| Aspect              | Composition     |
| ------------------- | --------------- |
| Relationship        | Has-a (strong)  |
| Coupling            | Low             |
| Ownership           | ✔ Yes           |
| Lifetime dependency | ✔ Strong        |
| Polymorphism        | ❌ No (directly) |

---

### Pros

* Better encapsulation
* Flexible design
* Easy to modify and extend
* Safer than inheritance

### Cons

* No polymorphism by default
* Requires delegation

---

## 4. Aggregation

### Definition

**Aggregation** represents a **weak has-a relationship**, where:

* One class **uses** another
* Ownership is **not implied**
* Lifetimes are **independent**

> **Aggregation implies association, not ownership.**

---

### Example

```cpp
class Employee {
public:
    void work() {}
};

class Department {
private:
    Employee* emp;   // Aggregation
public:
    Department(Employee* e) : emp(e) {}
};
```

✔ `Department` **has an** `Employee`
✔ Employee can exist without Department

---

### Characteristics

| Aspect              | Aggregation           |
| ------------------- | --------------------- |
| Relationship        | Has-a (weak)          |
| Coupling            | Low                   |
| Ownership           | ❌ No                  |
| Lifetime dependency | ❌ No                  |
| Polymorphism        | Possible via pointers |

---

### Pros

* Loose coupling
* Flexible object reuse
* Models real-world associations well

### Cons

* Ownership unclear if poorly designed
* Requires careful lifetime management

---

## 5. Key Differences (Side-by-Side)

| Feature        | Inheritance | Composition    | Aggregation     |
| -------------- | ----------- | -------------- | --------------- |
| Relationship   | Is-a        | Has-a (strong) | Has-a (weak)    |
| Ownership      | ❌           | ✔              | ❌               |
| Lifetime bound | ❌           | ✔              | ❌               |
| Code reuse     | Via base    | Via delegation | Via reference   |
| Polymorphism   | ✔           | ❌              | ✔ (if abstract) |
| Flexibility    | Low         | High           | High            |

---

## 6. Real-World Analogy

### Inheritance

* Dog **is an** Animal

### Composition

* Car **has an** Engine
  (Destroy Car → Engine destroyed)

### Aggregation

* Team **has** Players
  (Players exist independently)

---

## 7. When to Use What

### Use Inheritance When:

* Relationship is truly **is-a**
* Base class is designed for inheritance
* Polymorphism is required

### Use Composition When:

* You want **ownership**
* Behavior reuse without tight coupling
* You want safer, flexible design

### Use Aggregation When:

* Objects have independent lifetimes
* Relationship is temporary or optional
* Modeling real-world associations

---

## 8. Design Rule (VERY IMPORTANT)

> **Favor Composition over Inheritance**

Why?

* Composition avoids fragile hierarchies
* Changes don’t ripple through subclasses
* Design stays flexible

Inheritance should be a **last resort**, not a default.

---

## 9. Common Design Mistakes

* Using inheritance just for code reuse
* Modeling has-a relationships with inheritance
* Ignoring object lifetime ownership
* Overusing deep inheritance hierarchies


---

## Key Takeaways

* Inheritance models **is-a**

* Composition models **strong has-a**

* Aggregation models **weak has-a**

* Composition is generally preferred

* Choose relationship based on **ownership and lifetime**

* Correct choice leads to **maintainable, scalable systems**
