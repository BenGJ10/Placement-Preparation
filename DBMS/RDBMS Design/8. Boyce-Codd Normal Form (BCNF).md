# Boyce–Codd Normal Form (BCNF)

**Boyce–Codd Normal Form (BCNF)** is a **stronger and more rigorous version of Third Normal Form (3NF)**.  

It removes certain anomalies that **3NF still allows**, ensuring that **every determinant in a relation is a candidate key**.

BCNF is especially important when dealing with **multiple candidate keys** and **complex functional dependencies**.

---

## 1. Prerequisites for BCNF

A relation must first:
- Be in **First Normal Form (1NF)**
- Be in **Second Normal Form (2NF)**
- Be in **Third Normal Form (3NF)**

BCNF strengthens the dependency rule further.

---

## 2. Definition of Boyce–Codd Normal Form

A relation **R** is in **BCNF** if:

> For every non-trivial functional dependency **X → Y**,  
> **X must be a superkey** of the relation.

### Key Idea
- **Every determinant must be a candidate key**
- No attribute should determine another unless it uniquely identifies the entire tuple

---

## 3. BCNF vs 3NF (Core Difference)

3NF allows some dependencies where:
- X is not a superkey
- Y is a **prime attribute**

BCNF **does not allow this exception**.

| Condition | 3NF | BCNF |
|---------|-----|------|
| X is superkey | ✔ Allowed | ✔ Allowed |
| Y is prime attribute | ✔ Allowed | ❌ Not allowed |
| Strictness | Moderate | Very strict |

---

## 4. Example – Relation in 3NF but NOT in BCNF

Consider relation:
```
R(Student, Course, Instructor)
```

Functional Dependencies:
```
(Student, Course) → Instructor
Instructor → Course
```

Candidate Keys:
```
(Student, Course)
(Student, Instructor)
```

---

### Why This Violates BCNF

- **Instructor → Course**
- Instructor is **not a superkey**
- Violates BCNF condition

But:
- Course is a **prime attribute**
- So relation **satisfies 3NF**

This is a classic case where **3NF is not enough**, but BCNF is violated.

---

## 5. Decomposing into BCNF

### Step 1: Identify violating FD

```
Instructor → Course
```

### Step 2: Decompose

Create:
```
R1(Instructor, Course)
R2(Student, Instructor)
```

---

### Step 3: Check BCNF

- In R1: Instructor is key → BCNF satisfied  
- In R2: Student + Instructor is key → BCNF satisfied  

Decomposition is:
- **Lossless**
- May or may not be **dependency preserving**

---

## 6. BCNF Decomposition Algorithm

**1.** Identify a functional dependency X → Y that violates BCNF  

**2.** Decompose R into:
   - R1(X ∪ Y)
   - R2(R − Y + X)

**3.** Repeat until all relations satisfy BCNF

---

## 7. Lossless Join Guarantee in BCNF

BCNF decomposition is always:
- **Lossless**

Because decomposition is done using functional dependencies.

However:
- It is **not guaranteed to preserve all dependencies**

---

## 8. Dependency Preservation Issue in BCNF

Unlike 3NF:
- BCNF may break some dependencies
- Some constraints may require joining tables to verify

This is why **3NF is sometimes preferred in practice**.

---

## 9. Another Example

Relation:
```
R(A, B, C)
```

FDs:
```
A → B
B → C
```

Candidate Key:
```
A
```

Violation:
- B → C (B is not superkey)

### Decompose:
```
R1(B, C)
R2(A, B)
```

Both now satisfy BCNF.

---

## 10. When to Use BCNF vs 3NF

| Scenario | Preferred Form |
|--------|----------------|
| Strong correctness needed | BCNF |
| Dependency preservation important | 3NF |
| Simple schemas | BCNF |
| Performance-critical systems | 3NF |
| Educational / theoretical | BCNF |

---

## Key Takeaways

- BCNF eliminates anomalies that 3NF can still allow  

- Ensures **strong dependency correctness**  

- Guarantees **lossless decomposition**  

- May sacrifice **dependency preservation**  

- Used when correctness > enforcement simplicity
