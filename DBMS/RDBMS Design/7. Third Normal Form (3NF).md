# Third Normal Form (3NF)

**Third Normal Form (3NF)** is an extension of **Second Normal Form (2NF)**.  

A relation is in 3NF when it eliminates **transitive dependencies**, ensuring that **non-key attributes depend only on candidate keys and nothing else**.

3NF is one of the **most commonly used normal forms in real-world database design** because it provides a strong balance between **data integrity and performance**.

---

## 1. Prerequisites for 3NF

Before a relation can be in **Third Normal Form**, it must:

1. Be in **First Normal Form (1NF)**  
2. Be in **Second Normal Form (2NF)**  

Only after removing:
- multivalued attributes (1NF), and  
- partial dependencies (2NF),  

can we address **transitive dependencies**.

---

## 2. What is Transitive Dependency?

### Definition
A **transitive dependency** exists when:

> A non-prime attribute depends on **another non-prime attribute**, instead of directly depending on a candidate key.

Formally:
```
X → Y
Y → Z
```

where:
- X is a candidate key  
- Y is a non-prime attribute  
- Z is a non-prime attribute  

Then:
```
X → Z (transitively)
```

---

## 3. Why Transitive Dependency is a Problem

Transitive dependencies cause:

- **Redundancy**  
- **Update anomalies**  
- **Insertion anomalies**  
- **Deletion anomalies**

Because the same fact is stored **multiple times indirectly**, changes become difficult and error-prone.

---

## 4. Definition of Third Normal Form (3NF)

A relation **R** is in **Third Normal Form (3NF)** if:

1. R is in **2NF**, and  
2. **No non-prime attribute is transitively dependent on any candidate key**

### Equivalent Formal Definition
For every functional dependency:
```

X → A

```
at least one of the following must be true:
- X is a **superkey**, or  
- A is a **prime attribute** (part of some candidate key)

---

## 5. Example – Relation NOT in 3NF

Consider the relation:

```
Employee(EmpID, EmpName, DeptID, DeptName)
```

Candidate key:
```
EmpID
```

Functional Dependencies:
```
EmpID → EmpName
EmpID → DeptID
DeptID → DeptName
```

### Identify the Problem

- EmpID → DeptID  
- DeptID → DeptName  

So:
```

EmpID → DeptName (transitively)

```

Here:
- DeptName is a non-prime attribute  
- Depends on another non-prime attribute (DeptID)  

This is a **transitive dependency**  
→ Relation is **NOT in 3NF**

---

## 6. Converting to 3NF (Decomposition)

To remove the transitive dependency, decompose the relation.

### Decomposition

1. **Employee Table**

```
Employee(EmpID, EmpName, DeptID)
```

2. **Department Table**

```
Department(DeptID, DeptName)
```

Now:
- All non-key attributes depend **directly on keys**
- No transitive dependency exists
- Relation is in **3NF**

---

## 7. Another Example

Relation:

```
Student(RollNo, Name, HostelID, HostelName)
```

FDs:
```
RollNo → Name
RollNo → HostelID
HostelID → HostelName
```

Problem:
```
RollNo → HostelName (transitive)
```

### 3NF Decomposition

- Student(RollNo, Name, HostelID)
- Hostel(HostelID, HostelName)

---

## 8. 1NF vs 2NF vs 3NF

| Aspect | 1NF | 2NF | 3NF |
|--------|-----|-----|-----|
| Removes | Multivalued attributes | Partial dependencies | Transitive dependencies |
| Key Focus | Atomicity of data | Full dependency on keys | Non-key attributes depend only on keys |
| Anomalies Solved | Some | More | Most |
| Result | Basic structure | Reduced redundancy | High integrity|

---

## 9. Advantages of 3NF

| Advantage | Explanation |
|---------|-------------|
| Eliminates transitive dependency | Removes indirect redundancy |
| Reduces anomalies | Prevents update/insert/delete issues |
| Improves data integrity | Clear dependency structure |
| Widely practical | Used in most production databases |

---

## 10. Limitations of 3NF

**Even in 3NF:**

- Some redundancy may still exist

- Certain functional dependencies may violate **BCNF**

Hence, **BCNF** is a stricter form of normalization.

---

## Key Takeaways

- 3NF eliminates **transitive dependency**  

- Ensures **non-key attributes depend only on candidate keys**  

- Greatly reduces redundancy and anomalies  

- Most relational databases aim for **3NF**  

- BCNF is stricter but not always required
