# Functional Dependencies and Their Types

Functional Dependencies are the **foundation of relational database design** and play a critical role in **normalization**, **schema refinement**, and **ensuring data integrity**.  

Understanding FDs deeply helps in mastering Normal Forms (1NF → BCNF) and designing efficient, anomaly-free databases.

---

## 1. What is a Functional Dependency?

### Definition
A **Functional Dependency (FD)** is a constraint between two sets of attributes in a relation.  
An FD **X → Y** means:

> For every unique value of **X**, there is exactly one associated value of **Y**.

This means: **X determines Y**.

In this notation:
**X is the determinant**, and **Y is the dependent**.

---

### Example

| RollNo | Name | Dept |
|--------|------|------|
| 101    | Raj  | CSE  |
| 102    | Meera| ECE  |

Here:
- **RollNo → Name** (Roll number uniquely identifies the student)
- **RollNo → Dept** 

Thus:
```

RollNo → {Name, Dept}

```

## 2. Why Functional Dependencies Matter

Functional dependencies help identify:
- **Keys** (candidate keys, super keys)
- **Redundancy** in tables
- **Update anomalies**
- How to split tables during normalization
- Whether a schema satisfies 2NF, 3NF, or BCNF

FDs form the basis of all **normalization rules**.

---

## 3. Types of Functional Dependencies

Let’s go through all major types, with clean explanations and examples.

### 3.1 Trivial Functional Dependency

**Definition**: 
A functional dependency **X → Y** is *trivial* if **Y is a subset of X**.

Examples:
- `{RollNo, Name} → RollNo`
- `{A, B} → A`

Trivial FDs do not provide new information; they always hold.


### 3.2 Non-Trivial Functional Dependency

**Definition**: FD **X → Y** is non-trivial if **Y is NOT a subset of X**.

Example:
- RollNo → Name  
(“Name” is not part of “RollNo”)

Most useful FDs in design are non-trivial.


### 3.3 Completely Non-Trivial FD

If **X and Y have no common attributes**, i.e.,
```

X ∩ Y = Ø

```

Example:
- RollNo → PhoneNumber  
No overlap → completely non-trivial.


### 3.4 Partial Dependency

**Definition**: A **Partial Dependency** occurs when:
- X → Y is a valid FD
- X is **not a whole candidate key**
- Y depends on only a **part** of a composite key

Consider table:
```

(StudentID, CourseID, InstructorName)

```

Composite key: {StudentID, CourseID}

If:
```

StudentID → InstructorName

```

This is a **partial dependency** because only part of the composite key determines InstructorName.

#### Why it’s bad?
Creates redundancy → violates **2NF**.

### 3.5 Full Functional Dependency

**Definition**: 
Y is fully functionally dependent on X if:
- X → Y  
- Removing any attribute from X makes dependency invalid.

#### Example
(FilmID, Language) → SubtitleFile

Removing either FilmID or Language would no longer uniquely determine SubtitleFile.

This is acceptable and required for **2NF**.

### 3.6 Transitive Dependency

**Definition**: A dependency **X → Z** is *transitive* if:
- X → Y  
- Y → Z  
- And Y is not a key

#### Example:
```

RollNo → DeptID
DeptID → DeptName

```

Thus:
```

RollNo → DeptName (transitively)

```

#### Why bad?
This causes update anomalies → violates **3NF**.


### 3.7 Multivalued Dependency (MVD)

**Definition**: 
A multivalued dependency exists when an attribute A determines a **set of values** for attribute B, independently of other attributes.

Notation:
```

A →→ B

```

#### Example
In a table storing:
- Student
- Hobby
- LanguageKnown

A student may have multiple hobbies and multiple languages independently.

Thus:
```

Student →→ Hobby
Student →→ LanguageKnown

```

Used to identify 4NF violations.


### 3.8 Join Dependency (JD)

**Definition**: 
A relation R has a join dependency if:
```

R = Join(R1, R2, R3, ...)

```
but splitting and rejoining can maintain data consistency.

Used in **5NF (Project-Join Normal Form)**.


### 3.9 Equivalence of Functional Dependencies

Two sets of FDs F and G are equivalent if:
- F logically implies all FDs in G  
- G logically implies all FDs in F

This helps minimize dependency sets.

## 4. Armstrong’s Axioms (Rules for Working with FDs)

### 1. Reflexivity
If Y ⊆ X → X → Y  

### 2. Augmentation
If X → Y → XZ → YZ  

### 3. Transitivity
X → Y and Y → Z → X → Z  

These axioms help derive all other FDs and test normal forms.

---

## 5. Closure of Functional Dependencies

**Definition**
FD Closure (F⁺) is the set of *all* FDs that can be inferred from a given set of F.

### Why it’s important?
- To find keys  
- To test normalization  
- To detect redundancy  

---

## Summary Table

| Type of FD | Meaning | Normal Form Impact |
|------------|---------|--------------------|
| **Trivial** | Y ⊆ X | Always holds |
| **Non-trivial** | Y not subset of X | Used in schema design |
| **Partial** | Part of composite key determines attribute | Violation of **2NF** |
| **Full** | Entire key determines attribute | Good for 2NF |
| **Transitive** | Attribute depends on non-key via another attribute | Violation of **3NF** |
| **Multivalued** | One attribute determines multiple independent values | Violation of **4NF** |
| **Join** | Table can be reconstructed from smaller tables | Used in **5NF** |

---

## Key Takeaways

- FDs show how attributes relate in a table.  

- They help detect anomalies and guide normalization.  

- Partial, transitive, and multivalued dependencies indicate poor design.  

- Armstrong’s axioms allow deriving and validating dependencies.  

- FDs are essential for finding keys, splitting tables, and ensuring data integrity.
