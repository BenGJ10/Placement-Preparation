# Decomposition in Database Design

**Decomposition** is the process of breaking a relation (table) into **two or more smaller relations** while preserving important properties such as **no data loss**, **integrity of data**, and **ability to reconstruct the original relation**.  

Decomposition is a core concept in **normalization** and helps eliminate redundancy, anomalies, and inconsistency in relational databases.

---

## 1. What is Decomposition?

### Definition
Decomposition is the process of splitting a relation **R** into two or more relations **R₁, R₂, … Rn** such that:

> The new relations contain the same information as the original relation, ideally **without redundancy or spurious data**.

The goal is not just to split tables, but to **improve design quality** while maintaining correctness.

---

### Example

Original Relation **R(StudentID, StudentName, Dept, HOD)**

We decompose R into:

- R₁(StudentID, StudentName, Dept)  
- R₂(Dept, HOD)

Here:
- No information is lost  
- We removed repeated HOD information for every student  
- Decomposition reduced redundancy  

---

## 2. Why Decomposition is Needed

Badly designed relations lead to **anomalies**:

### 1. Update Anomaly
Updating the same fact at multiple places.

### 2. Insertion Anomaly
Cannot insert a record because some unrelated data is missing.

### 3. Deletion Anomaly
Deleting one fact unintentionally deletes another useful fact.

### 4. Redundancy
Repeated storage of the same data increases storage and inconsistency risk.

**Decomposition removes such problems** by structuring data correctly.

---

## 3. Types of Decomposition

Decomposition should ideally satisfy two major properties:

- **Lossless (Non-Loss) Decomposition**
- **Dependency-Preserving Decomposition**

It may also sometimes lead to:
- **Lossy Decomposition** (undesirable)

We discuss each below.

---

## 4. Lossless (Non-Loss) Decomposition

### Definition
A decomposition is **lossless** if the original relation **R** can be exactly **reconstructed** from decomposed relations using **natural join**:

```

R = R1 ⨝ R2

```

No extra tuples are generated, and no information is lost.

---

### Lossless Join Condition

Decomposition of **R** into **R1** and **R2** is **lossless** if:

> The attributes common to R1 and R2 form a **superkey** in at least one relation.

Formally:

```

(R1 ∩ R2) → R1
OR
(R1 ∩ R2) → R2

```

---

### Example of Lossless Decomposition

R(StudentID, Name, Dept, HOD)

Decompose into:

- R1(StudentID, Name, Dept)
- R2(Dept, HOD)

If:
```

Dept → HOD

```

Then decomposition is **lossless** because:
- Common attribute = Dept
- Dept is a key for R2

---

## 5. Lossy Decomposition

### Definition
A decomposition is **lossy** if joining decomposed relations produces **extra tuples that did not exist originally**.

This causes **spurious tuples** and ambiguity.

---

### Example of Lossy Decomposition

R(A, B, C)

Decompose into:

- R1(A, B)
- R2(A, C)

Common attribute = A

If **A is not a key**, join generates incorrect tuples.

---

### Why Lossy Decomposition is Bad

- Incorrect query answers  
- Data inconsistency  
- Loss of meaning  
- Cannot reconstruct original relation exactly  

Lossless decomposition is **mandatory**; lossy decomposition is **unacceptable**.

---

## 6. Dependency-Preserving Decomposition

### Definition
A decomposition is **dependency-preserving** if:

> All functional dependencies from the original relation can be enforced **without joining the decomposed relations**.

This ensures that **constraints can be checked locally** on each relation.

---

### Example

R(A, B, C)

FDs:
```

A → B
B → C

```

Decompose into:
- R1(A, B)
- R2(B, C)

All dependencies preserved → **dependency-preserving decomposition**

---

### Non-Dependency Preserving Decomposition

If enforcing some dependency requires recombining decomposed tables:

- More expensive  
- Hard to maintain constraints  
- Integrity enforcement becomes complex  

So dependency-preservation is **highly desirable**, though sometimes sacrificed for BCNF.

---

## 7. Goals of Good Decomposition

A good decomposition should:

| Goal | Explanation |
|------|-------------|
| **Lossless Join** | We must be able to reconstruct original relation |
| **Dependency Preserving** | FDs enforced without joins |
| **Remove Anomalies** | Eliminates redundancy & anomalies |
| **Reduce Redundancy** | Avoids repeated data |

---
## 8. Checking Decomposition Properties

### Standard Problem Format

Given:
```

R(A, B, C, D)
FDs:
A → B
C → D

```

Decompose:
```

R1(A, B)
R2(A, C, D)

```

Check lossless:

Common attribute = A

Since:
```

A → B (part of R1)

```

A is key for R1  
→ **Lossless decomposition**

---

## Summary Table

| Type | Meaning | Desirability |
|------|--------|--------------|
| **Lossless Decomposition** | No information loss | Essential |
| **Lossy Decomposition** | Produces spurious tuples | Not acceptable |
| **Dependency Preserving** | All FDs enforceable locally | Highly desirable |
| **Non-Dependency Preserving** | Need join to check FDs | Less desirable |

---

## Key Takeaways

- Decomposition is used to **improve schema quality**

- Must be **lossless** to avoid information loss

- Should **preserve dependencies** for constraint enforcement

- Helps remove **update/insert/delete anomalies**

- Basis for **normalization and BCNF/3NF design**
