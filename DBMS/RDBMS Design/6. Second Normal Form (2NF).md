# Second Normal Form (2NF)

**Second Normal Form (2NF)** builds directly on **First Normal Form (1NF)**.  

A relation is in 2NF when:

1. It is already in **1NF**, and  
2. It has **no partial dependency** of any non-prime attribute on a candidate key.

2NF mainly deals with the problem of **partial dependency** that arises in tables having **composite primary keys**.

---

## 1. Prerequisites for 2NF

Before achieving 2NF, the relation must:

- satisfy **1NF**
- have a clearly identified **primary/candidate key(s)**

---

## 2. What is Partial Dependency?

### Definition
A **partial dependency** occurs when:

> A non-prime attribute depends on **part of a composite key**, not on the whole key.

- **Prime attribute** → part of any candidate key  
- **Non-prime attribute** → not part of any candidate key  

---

### Example of Partial Dependency

Consider relation:

```

R(StudentID, CourseID, Instructor, Department)

```

Composite key:
```

(StudentID, CourseID)

```

Functional dependencies:
```

StudentID → Department
(StudentID, CourseID) → Instructor

```

Here:
- Department depends only on **StudentID**, not on whole composite key  
- This is **partial dependency**

Therefore, the table is **NOT in 2NF**.

---

## 3. Definition of Second Normal Form

A relation is in **2NF** if:

1. It is in **1NF**
2. **Every non-prime attribute is fully functionally dependent** on the **entire candidate key**

### Meaning
No non-key attribute depends on part of a candidate key.

> 2NF removes **partial dependencies**.

---

## 4. Converting to 2NF (Decomposition)

### Example Not in 2NF

Relation:
```

Result(RollNo, Subject, Marks, StudentName)

```

Candidate key:
```

(RollNo, Subject)

```

Functional Dependencies:
```

(RollNo, Subject) → Marks
RollNo → StudentName

```

### Problem
- StudentName depends only on RollNo  
- Partial dependency exists  
- Violates **2NF**

---

### Convert to 2NF

Decompose:

1. Student table
```

Student(RollNo, StudentName)

```

2. Result table
```

Result(RollNo, Subject, Marks)

```

Now:
- Each non-key attribute depends on the **whole key**
- No partial dependency remains
- Relation is now **in 2NF**

---

## 5. Another Example

Table:
```

OrderID, ProductID, ProductName, Quantity

```

Composite key:
```

(OrderID, ProductID)

```

Functional Dependencies:
```

(OrderID, ProductID) → Quantity
ProductID → ProductName

```

Here:
- ProductName depends only on ProductID
- Partial dependency → violates 2NF

### After 2NF decomposition

Tables:

**OrderDetails**
```

OrderID, ProductID, Quantity

```

**Product**
```

ProductID, ProductName

```

---

## 6. 1NF vs 2NF

| Aspect | 1NF | 2NF |
|--------|-----|-----|
| Focus | Atomic values, no repeating groups | Remove partial dependency |
| Concern | Unstructured tables | Composite keys |
| Removes | Multivalued and repeating attributes | Partial dependency |
| Still Allows | Transitive dependency | Not allowed |

---

## 7. Key Characteristics of 2NF

To be in 2NF:

- Must be in **1NF**
- No partial dependency
- Non-key attributes must depend on **whole key**
- Composite keys are important consideration

---

## 8. Benefits of 2NF

| Benefit | Explanation |
|---------|-------------|
| Removes redundancy | Same information not repeated |
| Eliminates anomalies | Prevents update, insert, delete anomalies |
| Clear table design | Separates independent entities |
| Better data integrity | Prevents inconsistent values |

---

## 9. Limitations of 2NF

Even after reaching 2NF, tables may still have:

- **transitive dependencies**
- update anomalies
- redundancy due to non-key dependencies

These issues are handled in **Third Normal Form (3NF)**.

---

## Key Takeaways

- 2NF eliminates **partial dependency**

- Mainly applicable when **composite keys exist**

- Every non-prime attribute must depend on **entire candidate key**

- 2NF improves design but **3NF is still required**
