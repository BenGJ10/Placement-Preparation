# Problems in Concurrency Control

Concurrent execution of transactions can cause **data inconsistency** if not properly managed. Understanding these problems is critical for placement interviews.

---

## 1. Overview

**Classification of Concurrency Problems:**
```
Dirty Read           - Read uncommitted data
Lost Update          - One transaction's update overwritten
Unrepeatable Read    - Same read returns different values
Phantom Read         - Different set of rows at different times
Cascading Rollback   - One abort forces others to abort
```

---

## 2. Dirty Read (Uncommitted Read)

A transaction **reads data written by another uncommitted transaction**.

```
T1: write(X) = 50 (uncommitted)
T2: read(X) = 50   ← DIRTY READ!
T1: ROLLBACK (X reverts)
T2: Used invalid value 50!
```

**Problem:** T2 operates on invalid data; consistency violated.

**Example:**
```
T1: Transfer $100 (uncommitted)
T2: Check balance, sees new value
T1: ROLLBACK
T2: Processed invalid balance!
```

---

## 3. Lost Update

**Two transactions update same data**, one update is **overwritten** and lost.

```
Initial: X = 100

T1: read(X)=100     T2: read(X)=100
T1: write(X)=110
T2: write(X)=120    ← Overwrites T1's update!

Final: X = 120 (T1's update lost!)
```

**Bank Example:**
```
T1: Withdraw $100  → X = 900
T2: Deposit $50    → X = 1050 (should be 950!)

Lost: T1's $100 withdrawal!
```

---

## 4. Unrepeatable Read

A transaction reads **same data twice and gets different values**.

```
T1: read(X) = 100
    ↓ (T2 updates and commits)
T1: read(X) = 200  ← Different value!
```

**Problem:** Inconsistent reads within transaction.

**Example:**
```
T1: Check credit score = 750 (approve?)
    ↓ (score updated by T2)
T1: Read score = 650 (reject!)
Inconsistent approval logic!
```

---

## 5. Phantom Read

A transaction's **query returns different sets of rows** at different times.

```
T1: SELECT * FROM students WHERE age > 20
    → Returns 5 students
    ↓ (T2 inserts age=25 student)
T1: SELECT * FROM students WHERE age > 20
    → Returns 6 students (PHANTOM!)
```

**Problem:** Different datasets violate transaction assumption.

**Audit Example:**
```
T1: Count employees hired in Jan 2024 = 10
    ↓ (T2: Insert new employee)
T1: Count again = 11
Audit numbers don't match!
```

---

## 6. Cascading Rollback

When one transaction aborts, **others that depend on it must also abort**.

```
T1: write(X)
T2: read(X), commit
T3: read(T2's result), commit

T1: ROLLBACK
↓ T2 must rollback (read invalid)
↓ T3 must rollback (used T2's result)

All three aborted!
```

**Impact:** Performance degradation, wasted computation.

## 7. Problem Summary Table

| Problem | Cause | Impact | When |
|---------|-------|--------|------|
| **Dirty Read** | Read uncommitted | Invalid data | No isolation |
| **Lost Update** | Concurrent write | Data loss | Low isolation |
| **Unrepeatable Read** | Concurrent update | Inconsistency | Low isolation |
| **Phantom Read** | Concurrent insert | Wrong aggregates | Low isolation |
| **Cascading** | Dirty read + abort | Multiple rollbacks | Very low isolation |

---

## 8. Isolation Levels (SQL Standard)

**Four standard levels protecting against problems:**

### 1. Read Uncommitted
```
Allows: Dirty reads, unrepeatable reads, phantoms
Performance: Fastest
Use: Non-critical operations only
```

### 2. Read Committed (Most common)
```
Prevents: Dirty reads
Allows: Unrepeatable reads, phantoms
Performance: Good balance
Use: Standard choice
```

### 3. Repeatable Read
```
Prevents: Dirty reads, unrepeatable reads
Allows: Phantom reads
Performance: Fair
Use: When consistency needed
```

### 4. Serializable (Strictest)
```
Prevents: All anomalies (dirty, unrepeatable, phantom)
Performance: Slowest
Use: Critical applications
```

## 10. Real-World E-commerce Scenario

```
Product: Laptop, Stock = 5

T1: Check stock → see 5
T2: Place order  → read stock, stock=4
T1: Make decision based on 5
    But stock is now 4! → Unrepeatable read

T3: Insert new laptop
T1: Query for totals = different result → Phantom read

Multiple problems in one scenario!
```

---

## 11. Best Practices

**Choose isolation level based on risk:**
```
Financial: SERIALIZABLE
Standard: READ COMMITTED  
Analytics: READ UNCOMMITTED
```

**Minimize lock scope:**
- Keep transactions small
- Commit frequently
- Avoid long-running queries

---

## Key Takeaways

- **Dirty read** most critical (uncommitted data).

- **Lost update** dangerous in financial systems.

- **Unrepeatable/phantom reads** violate transaction assumptions.

- **Cascading rollback** performance problem.

- **Isolation levels** provide graduated protection.

- Interview focus: **identify problem from scenario, recommend isolation level, explain prevention**.
