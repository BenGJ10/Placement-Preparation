# Recoverability in Transactions

**Recoverability** ensures transactions **recover from failures** while maintaining **database consistency** — preventing failed transactions from corrupting the database.

---

## 1. What is Recoverability?

A schedule is **recoverable** if transactions that read data commit only after transactions that write that data have committed.

```
If T2 reads from T1:
  T1 must commit before T2 commits
  ✓ If T1 fails, only T1 rollbacks
```

---

## 2. Cascading Rollback Problem

When one transaction rolls back, **dependent transactions must also rollback** (cascade effect).

```
T1: write(X) → T2: read(X), commit → T3: read(T2's result)

T1: ROLLBACK
  ↓ T2 must rollback (read uncommitted)
  ↓ T3 must rollback (used T2's result)
```

**Impact:** Performance degradation, wasted computation.

---

## 3. Schedule Types by Recoverability

| Type | Rule | Cascading | Safety |
|------|------|-----------|--------|
| **Recoverable** | T1 commits before T2 | Possible | Basic |
| **Cascadeless** | Read only committed | No | Good |
| **Strict** | No reads/writes until commit | No | Max |

**Hierarchy:** Strict ⊂ Cascadeless ⊂ Recoverable

---

## 4. Examples

### Recoverable Schedule
```sql
T1: write(X)
T2: read(X)
T1: commit()  ← Before T2
T2: commit()
✓ T1 committed before T2
```

### Cascadeless Schedule
```sql
T1: write(X)
T1: commit()  ← Before T2 reads
T2: read(X)
T2: commit()
✓ T2 reads only committed data
```

### Strict Schedule
```sql
T1: write(X)
(no other transaction touches X until T1 commits)
T1: commit()
T2: read(X)
✓ Maximum isolation
```

---

## 5. Log-Based Recovery

**What is logged:**
```
<start, T1>                   Transaction begins
<T1, write, X, old, new>      Write operation
<commit, T1>                  Commit marker
```

**Recovery algorithm:**
1. Scan log from start
2. Identify committed transactions (have COMMIT)
3. Identify uncommitted transactions (no COMMIT)
4. REDO committed changes (replay new values)
5. UNDO uncommitted changes (restore old values)

---

## 6. Checkpoints

A **checkpoint** is a database snapshot that speeds up recovery.

```
Without checkpoint:
  Crash → Scan entire log → Slow recovery

With checkpoint:
  Crash → Scan only from checkpoint → Fast recovery
```

**Process:**
1. Stop new transactions
2. Wait for active transactions to finish
3. Write all buffers to disk
4. Mark checkpoint in log
5. Resume transactions

---

## 7. Real-World Example: Bank Transfer

```
T1: Transfer $100 (A→B)
  write(A) = 900  (in buffer, uncommitted)

T2: Check balance
  read(A) = 1000  (from disk, safe)

T1: CRASH before commit

Recovery:
  Log shows: <T1, write, A, 1000, 900> NO COMMIT
  UNDO T1: A = 1000 ✓
  Database consistent
```

---

## 8. UNDO vs REDO

| Operation | Purpose | When Used |
|-----------|---------|-----------|
| **UNDO** | Rollback changes | Uncommitted transactions |
| **REDO** | Replay changes | Committed transactions |

---

## Key Takeaways

- **Recoverability** prevents database corruption after failures.

- **Cascadeless schedules** prevent cascading rollbacks.

- **Strict schedules** offer maximum isolation but lower concurrency.

- **Log-based recovery** uses UNDO (old values) and REDO (new values).

- **Checkpoints** dramatically reduce recovery time.

- Interview focus: **schedule types, failure recovery, UNDO/REDO, checkpoint benefits**.
