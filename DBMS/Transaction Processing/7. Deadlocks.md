# Deadlocks in Transaction Processing

**Deadlocks** occur when two or more transactions **wait indefinitely** for locks held by each other, causing the system to stall.

---

## 1. What is a Deadlock?

A **deadlock** is a situation where:
- Two or more transactions are blocked
- Each waits for a resource (lock) held by another
- No transaction can proceed
- System is stuck indefinitely

```
T1 holds A, waits for B
T2 holds B, waits for A
↓
Both waiting forever → DEADLOCK!
```

---

## 2. Deadlock Example

```
T1:                          T2:
Lock_X(A) ✓                  
read(A)
                             Lock_X(B) ✓
                             read(B)

Lock_X(B) ⏳ (waits)          Lock_X(A) ⏳ (waits)

↓ DEADLOCK (both waiting indefinitely)
```

---

## 3. Deadlock Conditions

**All four must be present for deadlock:**

1. **Mutual Exclusion:** Resources cannot be shared
2. **Hold and Wait:** Hold one lock, wait for another
3. **No Preemption:** Cannot forcibly take locks
4. **Circular Wait:** T1→T2→T3→T1

**If ANY condition absent → No deadlock**

---

## 4. Wait-for Graph Detection

**Nodes:** Transactions  
**Edges:** T1 → T2 means T1 waits for lock held by T2

### Cycle Detection

```
T1 → T2
T2 → T1  (cycle!)
↓
DEADLOCK!
```

### Examples

**Deadlock (cycle present):**
```
T1 → T2
T2 → T3
T3 → T1  (cycle!)
```

**No deadlock (acyclic):**
```
T1 → T2
T2 → T3
(no cycle)
```

---

## 5. Deadlock Prevention

### Strategy 1: Lock Ordering
All transactions acquire locks in **same predefined order**.

```
Rule: Always lock A before B before C

Result: Cannot have circular wait
```

### Strategy 2: Conservative 2PL
Get **all locks at once** before any operation.

```
T1: Lock_X(A), Lock_X(B), Lock_X(C)  ← All upfront
    [operations]
    unlock(...)

Result: No waiting after acquiring all locks
```

### Strategy 3: Timeout
If lock not acquired within time limit, **abort**.

```
T1: Try Lock_X(B)
    Wait X seconds
    If still waiting: ROLLBACK and retry
```

---

## 6. Deadlock Detection & Recovery

**Most common approach in practice.**

### Detection
```
1. Build wait-for graph continuously
2. Check for cycles periodically
3. If cycle found → Deadlock detected
4. Choose victim transaction
5. Rollback victim, others resume
```

### Victim Selection Criteria
Choose transaction with:
- Least work done
- Longest remaining time
- Lowest priority
- No external output yet
- Least cost to rollback

### Recovery
```
Steps:
1. Detect deadlock (cycle in graph)
2. Choose victim T
3. Rollback T (undo changes)
4. Release T's locks
5. Other waiting transactions proceed
6. Retry T later
```

---

## 7. Deadlock Handling Trade-offs

| Approach | Cost | Deadlock Occurs |
|----------|------|-----------------|
| **Prevention** | High (up-front) | Never |
| **Avoidance** | Medium | Early (prevented) |
| **Detection** | Low (until deadlock) | After detection |

**Most systems use Detection + Recovery** (detection cheapest until deadlock found).

## 8. Real-World Example: E-commerce

```
T1: Order laptop from warehouse A
    Lock_X(WarehouseA)
    read inventory
    
T2: Order monitor from warehouse B
    Lock_X(WarehouseB)
    read inventory
    
T1: Cross-warehouse transfer
    Lock_X(WarehouseB)  ⏳ (T2 has it)
    
T2: Cross-warehouse transfer
    Lock_X(WarehouseA)  ⏳ (T1 has it)

DEADLOCK!

System detects cycle: T1 → T2 → T1
Rolls back T2 (victim)
T1 proceeds
T2 retries
```

## 10. Symptoms of Deadlock

Watch for:
```
✗ Transactions never complete
✗ Application hangs
✗ No obvious errors (just waits)
✗ CPU idle (not computing)
✗ Multiple processes stuck
```

## Key Takeaways

- **Deadlock** = circular wait for locks (all transactions stall).

- **Wait-for graph** tool for detection (cycle = deadlock).

- **Detection + Recovery** most common (allow deadlock, then fix).

- **Prevention** via lock ordering (all transactions lock in same order).

- **Victim selection** minimizes rollback cost.

- Interview focus: **deadlock scenarios, wait-for graph, prevention vs detection, victim selection**.
