# Concurrency Control in Databases

**Concurrency Control** is the mechanism by which DBMS manages **simultaneous execution of multiple transactions** while maintaining **data consistency** and preventing conflicts.

---

## 1. What is Concurrency Control?

**Concurrency Control** encompasses all techniques used to:
- **Coordinate** simultaneous access to shared data
- **Prevent conflicts** between concurrent transactions
- **Ensure consistency** and isolation
- **Maximize throughput** while maintaining correctness

---

## 2. Core Problem

### Without Concurrency Control

```
Multiple transactions access same data simultaneously
           ↓
Conflicts occur
           ↓
Dirty reads, lost updates, phantom reads
           ↓
Data corruption and inconsistency
```

### With Concurrency Control

```
✓ Multiple concurrent transactions
✓ No conflicts or conflicts resolved
✓ Guaranteed consistency
✓ Good performance
```

---

## 3. Lock Types

### Shared Lock (Read Lock - S)

```
Allows: Multiple transactions read same data
Blocks: Exclusive locks by others

T1: Lock_S(X) ✓
T2: Lock_S(X) ✓ (multiple readers OK)
T3: Lock_X(X) ✗ (blocked)
```

### Exclusive Lock (Write Lock - X)

```
Allows: Only ONE transaction exclusive access
Blocks: Any other locks

T1: Lock_X(X) ✓
T2: Lock_S(X) ✗ (blocked)
T3: Lock_X(X) ✗ (blocked)
```

### Compatibility Matrix

| Current \ Request | **S** | **X** |
|---|---|---|
| **S** | ✓ | ✗ |
| **X** | ✗ | ✗ |

---

## 4. Two-Phase Locking (2PL)

**Most common and important protocol.**

### Phases

```
GROWING PHASE: Acquire locks
  [Lock A]
  [Lock B]
  [Lock C]

SHRINKING PHASE: Release locks
  [Unlock A]
  [Unlock B]
  [Unlock C]
```

**Rule:** Once first lock is released, no new locks acquired.

### Guarantee

✓ All 2PL schedules are **CONFLICT SERIALIZABLE**

### Variants

**Strict 2PL:** Hold all locks until COMMIT/ROLLBACK
```
Best for preventing cascading rollbacks
```

**Conservative 2PL:** Get all locks at beginning
```
Best for preventing deadlocks
```

---

## 5. Other Concurrency Control Methods

### Timestamp-Based Ordering

```
Each transaction gets unique timestamp
Operations ordered by timestamps
Prevents conflicts by timestamp rules
```

**Advantage:** No locks, no deadlocks
**Disadvantage:** Frequent restarts

### MVCC (Multi-Version Concurrency Control)

```
Multiple versions of each data item
Readers read older versions
Writers create new versions
Excellent concurrency
```

**Used in:** PostgreSQL, MySQL InnoDB, Oracle

### Optimistic Concurrency Control

```
Assume no conflicts
Validate at commit time
Rollback if conflict detected
```

**Good for:** Read-heavy workloads

## 6. Deadlock

### Problem

```
T1 holds A, waits for B (held by T2)
T2 holds B, waits for A (held by T1)
↓
DEADLOCK (both waiting indefinitely)
```

### Solution

**Detection + Recovery:**
```
1. Build wait-for graph
2. If cycle detected → Deadlock found
3. Choose victim transaction
4. Rollback victim
5. Others proceed
6. Retry victim
```

## 7. Isolation Levels

| Level | Protects Against | Concurrency | Use |
|-------|------------------|-------------|-----|
| **Read Uncommitted** | Nothing | Highest | Non-critical |
| **Read Committed** | Dirty reads | Good | Standard choice |
| **Repeatable Read** | Dirty + Unrepeatable | Fair | Strong consistency |
| **Serializable** | All anomalies | Lowest | Critical operations |

## 8. Real-World Example: Bank ATM

```
User A: Withdraw $100
User B: Check balance

Without control:
  A reads balance=1000
  B reads balance=1000
  A writes balance=900
  B writes balance=1000 ← Lost A's withdrawal!

With 2PL:
  A: Lock_X(balance)
  A: read, write, unlock
  B: Lock_S(balance)
  B: read, sees 900 ✓
```

## 9. Methods Comparison

| Method | Locks | Deadlock | Restarts | Best For |
|--------|-------|----------|----------|----------|
| **2PL** | Yes | Possible | No | General |
| **Timestamp** | No | No | Yes | Few conflicts |
| **MVCC** | Minimal | No | No | Read-heavy |
| **Optimistic** | No | No | Yes | Rare conflicts |

---

## 10. Lock Granularity

**Row-level:** Fine control, high overhead
**Page-level:** Balance
**Table-level:** Simple, low concurrency

**Trade-off:** More fine locks = more concurrency but more overhead

## Key Takeaways

- **Concurrency control** essential for concurrent safety.

- **Strict 2PL** prevents cascading rollbacks.

- **MVCC** modern approach with excellent concurrency.
