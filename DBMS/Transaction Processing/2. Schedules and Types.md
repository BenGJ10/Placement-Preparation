# Schedules and Schedule Types

A **Schedule** is the **sequence in which operations of concurrent transactions are executed**. Understanding schedules is crucial for determining if concurrent execution is safe.

---

## 1. What is a Schedule?

A **schedule** specifies the **chronological order** in which operations of multiple transactions are executed.

```
T1: read(A), write(B)
T2: read(B), write(A)

Possible schedule:
  T1.read(A)
  T1.write(B)
  T2.read(B)
  T2.write(A)
```

---

## 2. Types of Schedules

### Serial Schedule

**Transactions execute one after another** (no interleaving).

```
T1: read(A), write(B), commit
        ↓ (T1 completes)
T2: read(B), write(A), commit

Guaranteed correct but poor performance
```

### Interleaved Schedule

**Operations of transactions interleave**.

```
T1: read(A)
T2: read(B)
T1: write(B)
T2: write(A)
```

**May cause conflicts or be correct** (must be checked).

### Serializable Schedule

**Interleaved but result same as some serial order**.

```
Concurrent execution that
  ✓ Produces correct result
  ✓ Equivalent to some serial order
  ✓ Maintains consistency
```

---

## 3. Conflict Between Operations

Two operations **conflict** if:
1. **Different transactions**
2. **Same data item**
3. **At least one write**

```
T1.read(A) and T2.write(A)  → CONFLICT
T1.write(A) and T2.read(A)  → CONFLICT
T1.write(A) and T2.write(A) → CONFLICT
T1.read(A) and T2.read(A)   → NO conflict
```

---

## 4. Schedule Classification

### Recoverable Schedule

If T2 reads from T1, **T1 must commit before T2 commits**.

```
T1: write(X)
T2: read(X)
T1: commit()  ← Before T2 commits
T2: commit()

✓ If T1 fails, can rollback T1 only
```

### Cascadeless Schedule (ACA)

Transactions read **only committed data**.

```
T1: write(X)
T1: commit()  ← Before T2 reads
T2: read(X)

✓ No cascading rollbacks
```

### Strict Schedule

No reads/writes until previous writer commits.

```
T1: write(X)
(no one touches X until T1 commits)
T1: commit()
T2: read(X)

✓ Maximum safety
```

### Serializable Schedule

Equivalent to executing transactions serially.

```
Concurrent but result = some serial order

✓ Correct result
✓ Good performance
✓ Best of both worlds
```

---

## 5. Schedule Hierarchy

```
STRICT SCHEDULES
        ⊂
CASCADELESS (ACA)
        ⊂
RECOVERABLE
        ⊂
ALL SCHEDULES
```

**Meaning:** Every strict is cascadeless, every cascadeless is recoverable.

---

## 6. Testing Serializability

### Conflict Serializability

Check if schedule **conflict equivalent** to some serial order.

**Method:** Precedence graph
```
1. Create node for each transaction
2. For each conflicting pair:
   If op1 (T1) before op2 (T2):
     Add edge T1 → T2
3. If graph acyclic:
   Serializable (trace path for order)
4. If graph has cycle:
   NOT serializable
```

---

## 7. Example: Precedence Graph

### Serializable Schedule

```
T1.write(X)
T2.read(X)
T1.write(Y)
T2.write(Y)

Conflicts: T1.write(X) vs T2.read(X) → T1 → T2
           T1.write(Y) vs T2.write(Y) → T1 → T2

Graph: T1 → T2 (acyclic)

✓ Serializable (equivalent to T1 then T2)
```

### Non-Serializable Schedule

```
T1.write(A)
T2.write(A)
T1.read(B)
T2.read(B)
T1.write(B)

Conflicts:
  T1.write(A) vs T2.write(A) → T1 → T2
  T2.read(B) vs T1.write(B) → T2 → T1

Graph: T1 → T2 → T1 (CYCLE!)

✗ NOT serializable
```

---

## 8. Conflict vs View Serializability

| Type | Basis | Strictness | Used |
|------|-------|-----------|------|
| **Conflict** | Operation order | Stricter | Most DBMS |
| **View** | Read/write values | Looser | Rare |

**Relationship:**
```
Conflict Serializable ⊂ View Serializable

Every conflict serializable is view serializable
But not vice versa
```

---

## 9. Real-World Example: Concurrent Transfers

```
T1: Transfer $100 A→B
T2: Transfer $50 B→C

Serial order T1, T2:
  A=900, B=1100, C=50

Schedule:
  T1.read(A)=1000
  T2.read(B)=1000
  T1.write(A)=900
  T1.read(B)=1000
  T1.write(B)=1100
  T2.read(C)=0
  T2.write(B)=950  ← Overwrites T1!
  T2.write(C)=50

Result: A=900, B=950, C=50
Equivalent to T1 then T2? YES! (serializable)
```

---

## Summary Table

| Type | Property | Result |
|------|----------|--------|
| Serial | One after another | Always correct |
| Interleaved | Operations mix | May conflict |
| Serializable | Concurrent but correct | Safe |
| Recoverable | T1 commits before T2 | Rollback safe |
| Cascadeless | Read only committed | No cascades |
| Strict | No reads/writes | Most restrictive |

---

## Key Takeaways

- **Schedule** defines operation ordering.

- **Conflict** between operations matters (same data + at least one write).

- **Serializable** schedules are correct despite interleaving.

- **Precedence graph** tests serializability (acyclic = serializable).

- **Strict > Cascadeless > Recoverable** (hierarchy of safety).
