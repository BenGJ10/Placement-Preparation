# Serializability of Schedules

**Serializability** is a **correctness criterion** that ensures concurrent transaction schedules produce results **equivalent to executing transactions serially**.

It is the most important concept for verifying transaction correctness.

---

## 1. What is Serializability?

A **schedule is serializable** if its effect is **equivalent to executing transactions one after another** in some order.

```
Concurrent schedule (fast)
        ↓
Same result as serial schedule (correct)
        ↓
SERIALIZABLE!
```

---

## 2. Serial vs Serializable Schedule

### Serial Schedule

```
T1 completely executes → T2 completely executes → T3...

Guaranteed correct but NO parallelism
Result: Very slow
```

### Serializable Schedule

```
T1 and T2 interleave
BUT result = executing T1 then T2

✓ Concurrent execution
✓ Correct results
✓ Good performance
```

---

## 3. Conflict Serializability

### Definition

Two schedules are **conflict equivalent** if they have **same conflicting operations in same order**.

### Conflicting Operations

Operations conflict if:
- **Different transactions**
- **Same data item X**
- **At least one write**

```
T1.read(A) and T2.write(A)  → CONFLICT
T1.write(A) and T2.read(A)  → CONFLICT
T1.write(A) and T2.write(A) → CONFLICT
T1.read(A) and T2.read(A)   → NO conflict
```

---

## 4. Precedence Graph Testing

**Tool for checking conflict serializability:**

### Algorithm

```
1. Create node for each transaction
2. For each pair of conflicting operations:
   If op1 (T1) before op2 (T2):
     Add edge T1 → T2
3. Check for cycles:
   IF acyclic → SERIALIZABLE
   IF cycle → NOT SERIALIZABLE
```

### Example 1: Serializable

```
Schedule:
  T1.read(A)
  T1.write(B)
  T2.read(B)
  T2.write(A)

Conflicts:
  T1.write(B) vs T2.read(B) → T1 → T2

Graph: T1 → T2 (acyclic)

✓ SERIALIZABLE (equivalent to T1 then T2)
```

### Example 2: NOT Serializable

```
Schedule:
  T1.write(A)
  T2.read(A)
  T1.read(B)
  T2.write(B)
  T1.write(B)

Conflicts:
  T1.write(A) vs T2.read(A) → T1 → T2
  T2.write(B) vs T1.write(B) → T2 → T1

Graph: T1 → T2 → T1 (CYCLE!)

✗ NOT SERIALIZABLE
```

---

## 5. View Serializability

More general than conflict serializability.

**Two schedules are view equivalent** if:
1. Same initial reads
2. Same final writes
3. Same read-from relationships

**Relationship:**
```
Conflict Serializable ⊂ View Serializable

Every conflict serializable is view serializable
But some view serializable NOT conflict serializable
```

**Why rarely used:** Hard to check, only in edge cases.

---

## 6. Practical Example: Bank Transfer

```
Initial: A=1000, B=1000

T1: Transfer $100 (A→B)
  read(A), write(A)=900, read(B), write(B)=1100

T2: Transfer $50 (B→C)
  read(B), write(B)=950, read(C), write(C)=50

Concurrent execution:
  T1.read(A)=1000
  T2.read(B)=1000
  T1.write(A)=900
  T1.read(B)=1000
  T1.write(B)=1100
  T2.read(C)=0
  T2.write(B)=950  ← Overwrites T1!
  T2.write(C)=50

Result: A=900, B=950, C=50

Is this serializable?
  Equivalent to T1 then T2?
  A=900, B=950, C=50 ✓ YES!
```

## 7. Ensuring Serializability

**Method 1: Serial Execution**
```
Execute one transaction at a time
Result: Always serializable
Problem: No parallelism
```

**Method 2: 2-Phase Locking (2PL)**
```
Acquire locks in growing phase
Release locks in shrinking phase
Result: Guaranteed serializable
```

**Method 3: Timestamp Ordering**
```
Assign timestamps to transactions
Order operations by timestamps
Result: Serializable (with special rules)
```

**Method 4: MVCC**
```
Multiple versions of data
Readers see consistent version
Result: Serializable without heavy locking
```

---

## 8. Why Serializability Matters

```
Serializable → Consistent results
           → Predictable behavior
           → Data integrity
           → Concurrent execution

Non-serializable → Unpredictable results
                → Data corruption
                → Race conditions
```

## Key Takeaways

- **Serializability** ensures concurrent execution is correct.

- **Conflict serializability** most practical criterion.

- **Precedence graph** (acyclic = serializable, cyclic = not).

- **2-Phase Locking** guarantees conflict serializable schedules.

- **MVCC** modern alternative to locking.

- Interview focus: **precedence graphs, detecting conflicts, serializability testing, 2PL connection**.
