# What is Transaction Processing?

**Transaction Processing** is the mechanism by which **multiple database operations** are grouped together as a **single logical unit** that either **completely succeeds or completely fails**.

It is fundamental to maintaining **data consistency** and **reliability** in databases.

---

## 1. Definition

A **transaction** is a **sequence of database operations** (read/write) that:
- **Starts** with BEGIN
- **Ends** with COMMIT (success) or ROLLBACK (failure)
- **Succeeds completely** or **fails completely** (no partial success)

---

## 2. Transaction Lifecycle

```
1. START TRANSACTION
   ↓
2. Read/Write Operations (queries)
   ↓
3. COMMIT (all changes permanent)
   OR
   ROLLBACK (all changes undone)
```

---

## 3. ACID Properties

**A - Atomicity:** All-or-nothing (entire transaction succeeds or fails)

**C - Consistency:** Database state valid before and after transaction

**I - Isolation:** Concurrent transactions don't interfere

**D - Durability:** Committed changes survive crashes

---

## 4. Simple Example

```sql
BEGIN TRANSACTION;

UPDATE Account SET Balance = Balance - 100 WHERE ID = 1;
UPDATE Account SET Balance = Balance + 100 WHERE ID = 2;

-- If both succeed: COMMIT (permanent)
-- If any fails: ROLLBACK (undo both changes)

COMMIT;  -- OR ROLLBACK;
```

**Key:** Either both updates or neither (money not lost/created).

---

## 5. Real-World Scenarios

### Banking: Money Transfer

```
Transaction:
  Withdraw $100 from Account A
  Deposit $100 to Account B

If step 1 succeeds but step 2 fails:
  ROLLBACK (undo withdrawal)
  ✓ Money safe (not lost in between)
```

### E-commerce: Order Processing

```
Transaction:
  Insert order record
  Update inventory
  Charge credit card
  Send confirmation

All succeed → COMMIT
Any fails → ROLLBACK (order cancelled completely)
```

### Flight Booking: Seat Reservation

```
Transaction:
  Check seat availability
  Reserve seat
  Update booking status
  Send confirmation

Either all succeed or all fail
(No partial bookings)
```

---

## 6. Types of Transaction Processing

### OLTP (Online Transaction Processing)
```
- Short, frequent transactions
- Many concurrent users
- Each transaction small
- Example: Bank ATM, airline booking

Goal: Process maximum transactions quickly
```

### Batch Processing
```
- Large, infrequent transactions
- Few concurrent transactions
- Each transaction large
- Example: Monthly payroll, end-of-day reports

Goal: Process bulk data efficiently
```

---

## 7. Transaction States

```
START
  ↓
ACTIVE (running operations)
  ↓
PARTIALLY COMMITTED (operations done, not yet committed)
  ↓
COMMITTED (permanent)  OR  FAILED (abort/rollback)
  ↓
TERMINATED
```

---

## 8. Why Transactions Matter

**Without transactions:**
```
Partial writes → Data corruption
Concurrent conflicts → Race conditions
Crashes → Inconsistent state
```

**With transactions:**
```
Atomic operations → Always consistent
Isolation → Concurrent safety
Durability → Crash recovery
```

---

## 9. Transaction Control Commands

```sql
BEGIN TRANSACTION;      -- Start transaction
COMMIT;                 -- Commit (permanent)
ROLLBACK;               -- Rollback (undo)
SAVEPOINT name;         -- Create checkpoint
ROLLBACK TO name;       -- Rollback to checkpoint
```

---

## 10. Common Interview Questions

**Q: What is a transaction?**
A: Sequence of database operations that either all succeed or all fail as single unit.

**Q: Why do we need transactions?**
A: Ensure data consistency, prevent partial updates, handle concurrent access.

**Q: What happens if transaction fails midway?**
A: ROLLBACK undoes all changes made so far.
