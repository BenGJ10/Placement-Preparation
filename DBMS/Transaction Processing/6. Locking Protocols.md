# Locking Protocols in Databases

**Locking Protocols** are the **rules** by which transactions acquire and release locks to manage concurrent access to shared data.

The most important protocol is **Two-Phase Locking (2PL)**, which ensures serializability.

---

## 1. Lock Types

### Shared Lock (S-lock / Read Lock)

```
Allows: Multiple transactions read same data
Blocks: Exclusive locks by others

T1: Lock_S(X) ✓
T2: Lock_S(X) ✓ (multiple readers OK)
T3: Lock_X(X) ✗ (blocked)
```

**When used:** Before reading data

### Exclusive Lock (X-lock / Write Lock)

```
Allows: Only ONE transaction access
Blocks: Any lock by others

T1: Lock_X(X) ✓
T2: Lock_S(X) ✗ (blocked)
T2: Lock_X(X) ✗ (blocked)
```

**When used:** Before writing data

### Lock Compatibility Matrix

| Current \ Request | **S** | **X** |
|---|---|---|
| **S** | ✓ | ✗ |
| **X** | ✗ | ✗ |

## 2. Two-Phase Locking (2PL)

**Definition:** Transactions acquire and release locks in exactly **two phases**.

```
GROWING PHASE:      SHRINKING PHASE:
[Lock A]            [Unlock A]
[Lock B]            [Unlock B]
[Lock C] → transition point
```

**Rules:**
- Phase 1: Only acquire locks, never release
- Phase 2: Only release locks, never acquire

**Guarantee:** ✓ All 2PL schedules are **CONFLICT SERIALIZABLE**

---

## 3. 2PL Variants

### Basic 2PL
```
T1: Lock_X(A)
    Lock_X(B)           ← Growing
    Lock_X(C)
    unlock(A)           ← Shrinking (first unlock ends growing)
    unlock(B)
    unlock(C)
```

### Strict 2PL
```
Hold ALL locks until COMMIT
T1: Lock_X(A), Lock_X(B), Lock_X(C)
    [operations]
    COMMIT              ← All locks released at once
```

**Advantage:** Prevents cascading rollbacks

### Conservative 2PL
```
Get ALL locks at beginning
T1: Lock_X(A), Lock_X(B), Lock_X(C)  ← All upfront
    [operations]
    unlock(...)
```

**Advantage:** No deadlocks possible

## 4. Deadlock in Locking

**Situation:**
```
T1 holds A, waits for B (held by T2)
T2 holds B, waits for A (held by T1)
↓
DEADLOCK (both waiting forever)
```

### Wait-for Graph Detection

```
Nodes: Transactions
Edges: T1 → T2 means T1 waits for lock held by T2

Cycle in graph = Deadlock!
```

### Deadlock Resolution

```
1. Build wait-for graph continuously
2. If cycle detected:
   - Choose victim transaction
   - Rollback victim
   - Others proceed
   - Retry victim later
```

## 5. Practical Example: Bank Transfer

### Without Locking (Problem)

```
T1: Transfer $20 A→B
    read(A)=100
    write(A)=80

T2: Transfer $10 A→B
    read(A)=100     ← Lost T1's change!
    write(A)=90

Result: Inconsistency (should be 70)
```

### With Strict 2PL (Solution)

```
T1: Lock_X(A), Lock_X(B)
    read(A)=100, write(A)=80
    read(B)=100, write(B)=120
    unlock(A), unlock(B)
    commit()

T2: Waits for locks on A, B until T1 commits
    Then proceeds with current values
    
Result: Correct, serializable
```

## 6. Lock Granularity

### Levels

**Table-level:** Simple but low concurrency
```
Lock entire table
  T1: Lock_X(Employees)
  T2: Cannot access any row
```

**Row-level:** Complex but high concurrency
```
Lock individual rows
  T1: Lock_X(Employee row 5)
  T2: Can access other rows
```

**Page-level:** Balance between
```
Lock disk page (contains multiple rows)
```

### Lock Escalation

```
Row locks → Page locks → Table locks

When: Too many row locks
Why: Reduce overhead
```

## 7. Comparison: Lock Protocols

| Protocol | Deadlock | Cascading | Concurrency | Overhead |
|----------|----------|-----------|-------------|----------|
| Basic 2PL | Yes* | Yes | High | Low |
| Strict 2PL | Yes* | No | Low | Medium |
| Conservative | No | No | Very Low | High |

*Deadlock possible but detectable and recoverable

---

## 8. SQL Isolation Levels

**Map to locking protocols:**

```
SERIALIZABLE         → Strict 2PL
REPEATABLE READ      → Strict 2PL + range locks
READ COMMITTED       → Short S-locks
READ UNCOMMITTED     → No S-locks
```

## Key Takeaways

- **Two-Phase Locking** most important protocol.

- **Strict 2PL** prevents cascading rollbacks (recommended).

- **Lock types** (S, X) prevent conflicting access.

- **Deadlock** detected via wait-for graphs.

- **Lock granularity** balances concurrency vs overhead.

- Interview focus: **2PL phases, lock types, deadlock detection, protocols comparison**.
