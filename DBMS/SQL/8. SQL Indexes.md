# SQL Indexes

An **Index** in SQL is a **data structure** that improves the **speed of data retrieval** from a table.

It works like a **book's index** — instead of reading every page, you look up a topic and go directly to relevant pages.

> **Indexes speed up queries but slow down insertions and updates (because the index must also be updated).**

---

## Definition

- An **index** is a **database object** that stores a **sorted copy** of selected columns from a table.

- When you query data, the database uses the index to quickly locate rows **without scanning the entire table**.

- Indexes are **maintained automatically** when data is inserted, updated, or deleted.

---

## Why Indexes are Important

### Without Index
```
Query: SELECT * FROM Employees WHERE EmpID = 105
        ↓
Database scans entire table (1 million rows)
        ↓
Finds row 1,000,000+ operations
```

### With Index
```
Query: SELECT * FROM Employees WHERE EmpID = 105
        ↓
Database uses index (binary search)
        ↓
Finds row ~20 operations (log n)
        ↓
Much FASTER!
```

---

## Types of Indexes

### 1. Primary Key Index
- **Automatically created** for primary key
- **Unique** (no duplicates)
- **Fastest** lookups
- By default **clustered** (controls row order)

```sql
CREATE TABLE Employees (
  EmpID INT PRIMARY KEY,  -- Index automatically created
  Name VARCHAR(100)
);
```

### 2. Unique Index
- Ensures **no duplicate values** in column
- Used for columns that must be unique (email, username)

```sql
CREATE UNIQUE INDEX idx_email ON Users(Email);
```

### 3. Composite Index
- Index on **multiple columns**
- Order matters (used left-to-right)

```sql
CREATE INDEX idx_dept_salary ON Employees(Department, Salary);
```

### 4. Full-Text Index
- For **text search** in large documents
- Used with `MATCH` and `AGAINST`

```sql
CREATE FULLTEXT INDEX idx_content ON Articles(Content);
```

---

## Clustered vs Non-Clustered Index

| Aspect | Clustered | Non-Clustered |
|--------|-----------|---------------|
| **Count** | Only 1 per table | Multiple per table |
| **Storage** | Defines row order | Separate from data |
| **Speed** | Fastest | Fast |
| **Primary Key** | Usually clustered | Optional |

### Clustered Index Example
```
Table Employees sorted by EmpID (clustered index):

EmpID | Name    | Salary
------|---------|-------
101   | Alice   | 50000
102   | Bob     | 70000
103   | Carol   | 75000

Rows physically stored in this order
```

### Non-Clustered Index Example
```
Index on Department:

Department | EmpID
-----------|-------
HR         | 101
IT         | 102, 103
Sales      | 104

Points to rows (not sorted by this index)
```

## Syntax

### Create Index
```sql
CREATE INDEX idx_name ON table_name(column_name);
```

### Create Unique Index
```sql
CREATE UNIQUE INDEX idx_unique ON table_name(column_name);
```

### Create Composite Index
```sql
CREATE INDEX idx_composite ON table_name(col1, col2);
```

### Drop Index
```sql
DROP INDEX idx_name;
```

---

## Examples

### Example 1: Simple Index
```sql
CREATE INDEX idx_salary ON Employees(Salary);

-- Now this query is fast:
SELECT * FROM Employees WHERE Salary > 50000;
```

### Example 2: Composite Index
```sql
CREATE INDEX idx_dept_salary ON Employees(Department, Salary);

-- Fast for queries on Department OR (Department + Salary):
SELECT * FROM Employees WHERE Department = 'IT' AND Salary > 60000;

-- Also fast for just Department:
SELECT * FROM Employees WHERE Department = 'IT';

-- NOT fast for just Salary (column not first):
SELECT * FROM Employees WHERE Salary > 50000;
```

### Example 3: Unique Index
```sql
CREATE UNIQUE INDEX idx_email ON Users(Email);

-- Now email must be unique:
INSERT INTO Users (Email) VALUES ('john@example.com');  -- OK
INSERT INTO Users (Email) VALUES ('john@example.com');  -- ERROR!
```

## Advantages of Indexes

✓ **Fast data retrieval** — Queries execute much faster  
✓ **Reduced I/O** — Fewer disk accesses needed  
✓ **Better performance** — Especially for WHERE, JOIN, ORDER BY  
✓ **Automatic maintenance** — Database updates indexes automatically  

---

## Disadvantages of Indexes

✗ **Slower insertions/updates** — Index must be updated  
✗ **Extra storage** — Indexes consume disk space  
✗ **Overhead** — Maintaining index has cost  
✗ **Too many indexes** — Slows down updates significantly  

---

## When to Use Indexes

### Use Indexes For
```
✓ Columns frequently used in WHERE clauses
✓ Columns used in JOIN conditions
✓ Columns used in ORDER BY
✓ Large tables with many rows
✓ Columns with many unique values
```

### Don't Use Indexes For
```
✗ Small tables
✗ Columns with few unique values
✗ Columns rarely queried
✗ Columns with many NULLs
✗ Tables with frequent inserts/updates
```

---

## Index Performance Impact

| Operation | Without Index | With Index |
|-----------|---------------|-----------|
| SELECT (WHERE) | Slow | Fast |
| INSERT | Fast | Slower |
| UPDATE | Fast | Slower |
| DELETE | Slow | Slower |

**Key Insight:** Indexes speed up reads but slow down writes.

---

## Real-World Example: E-commerce

### Scenario
```
Products table: 1 million rows

Query: Find all laptops priced under $1000
SELECT * FROM Products 
WHERE Category = 'Laptops' AND Price < 1000;
```

### Without Index
- Scans all 1 million rows
- ~1 second or more

### With Index on (Category, Price)
- Uses index to find matching rows
- ~10-50 milliseconds
- **50-100x faster!**

## Key Takeaways

- **Indexes** dramatically improve query performance.

- **Trade-off:** Fast reads vs. slower writes.

- **Composite indexes** better than multiple single-column indexes.

- **Too many indexes** hurt performance more than help.

- **Monitor index usage** — remove unused indexes.
