# Isolation in ACID

**Isolation** defines how a transaction is protected from the effects of **concurrent execution of other transactions**.  

It ensures that each transaction behaves **as if it were the only transaction** running in the system, even when many are executing at the same time.

Isolation is crucial for **correctness in multi-user databases**.

---

## 1. What is Isolation?

### **Definition**
Isolation ensures that:
> The intermediate (uncommitted) results of a transaction are **not visible** to other concurrent transactions.

Each transaction should see the database in a **consistent state**, unaffected by incomplete operations of others.

---

## 2. Why Isolation is needed

In real databases:
- Multiple users access the same data concurrently
- Transactions may overlap in time
- Without isolation, data corruption and incorrect results occur

Isolation prevents **read–write conflicts** and ensures predictable behavior.

---

## 3. Isolation vs Serial Execution

### Serial Execution
- Transactions execute **one after another**
- Always correct
- Very slow and impractical

### Concurrent Execution (with Isolation)
- Transactions execute **simultaneously**
- Higher throughput
- Must behave **as if serial**

Isolation ensures **serializability** while allowing concurrency.

---

## 4. Read Phenomena (Concurrency Anomalies)

When isolation is weak, the following problems occur.


### 4.1 Dirty Read

A transaction reads data written by another transaction that has **not yet committed**.

### Example
```
T1: UPDATE account SET balance = 500 WHERE id = 1;
T2: SELECT balance FROM account WHERE id = 1; -- reads 500
T1: ROLLBACK;
```

- T2 reads data that **never actually existed**
- Leads to incorrect decisions

**This is very dangerous**

---

### 4.2 Dirty Write

Two transactions overwrite each other's uncommitted data. 

### Example
```
T1: UPDATE balance = 500
T2: UPDATE balance = 300
T1: ROLLBACK
```

Now the final value is unpredictable.

**Must never be allowed**

---

### 4.3 Non-Repeatable Read
A transaction reads the **same row twice** and gets **different values** because another transaction modified it in between.

### Example
```
T1: SELECT balance FROM account WHERE id = 1; -- 1000
T2: UPDATE balance = 800 WHERE id = 1; COMMIT;
T1: SELECT balance FROM account WHERE id = 1; -- 800
```

- Causes inconsistent results within the same transaction
- T1 sees different values for the same data

---

### 4.4 Phantom Read

A transaction re-executes a query and sees **new rows** inserted or deleted by another transaction.

### Example
```
T1: SELECT * FROM orders WHERE amount > 500;
T2: INSERT INTO orders VALUES (101, 700); COMMIT;
T1: SELECT * FROM orders WHERE amount > 500;
```

- T1 sees **extra rows** (phantoms)

### Difference from Non-Repeatable Read
- Non-repeatable → existing row changes
- Phantom → new rows appear/disappear

---

## 5. Isolation Levels

The SQL standard defines **four isolation levels**, each allowing or preventing certain read phenomena.

### 5.1 Read Uncommitted

### Behavior
- Transactions can read **uncommitted data**

### Allowed Issues
- Dirty Read
- Non-Repeatable Read
- Phantom Read

### Use Case
- Rarely used
- High performance, low correctness

---

### 5.2 Read Committed

### Behavior
- Can read **only committed data**

### Prevents
✔ Dirty Reads

#### Allows
- Non-Repeatable Reads
- Phantom Reads

#### Use Case
- Default in **PostgreSQL, Oracle**
- Balance between safety and performance

---

### 5.3 Repeatable Read

### Behavior
- Rows read cannot change during the transaction

### Prevents
✔ Dirty Reads  
✔ Non-Repeatable Reads  

### Allows
- Phantom Reads (in theory, depending on DB)

### Use Case
- MySQL InnoDB default isolation level

---

### 5.4 Serializable

### Behavior
- Highest isolation
- Transactions behave **exactly as if executed serially**

### Prevents
✔ Dirty Reads  
✔ Non-Repeatable Reads  
✔ Phantom Reads  

### Cost
- Lowest concurrency
- Possible performance degradation

### Use Case
- Financial systems
- Critical data consistency

---

## 6. Isolation Levels vs Read Phenomena

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|-----------------|-----------|---------------------|--------------|
| Read Uncommitted | Yes | Yes | Yes |
| Read Committed | No | Yes | Yes |
| Repeatable Read | No | No | Yes |
| Serializable | No | No | No |

---

## 7. How Isolation is Implemented

Isolation is achieved using:

- **Locking mechanisms**
  - Shared locks (read)
  - Exclusive locks (write)

- **Multiversion Concurrency Control (MVCC)**
  - Maintains multiple versions of data
  - Readers don’t block writers

Modern DBs use **MVCC + locks** for performance and correctness.

---

## 8. Isolation vs Atomicity

| Aspect | Atomicity | Isolation |
|------|----------|-----------|
| Focus | All-or-nothing execution | Visibility between transactions |
| Prevents | Partial updates | Concurrency anomalies |
| Implemented by | Logging, rollback | Locks, MVCC |

---

## Key Takeaways

- Isolation controls **how transactions see each other’s changes**.

- Weak isolation leads to dirty reads, non-repeatable reads, and phantom reads.

- SQL defines four isolation levels with increasing strictness.

- Higher isolation → better correctness but lower concurrency.

- Serializable provides strongest guarantees but at performance cost.
