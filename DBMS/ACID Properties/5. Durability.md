# Durability in ACID

**Durability** is the ACID property that guarantees that **once a transaction is committed, its effects are permanent**, even in the presence of system crashes, power failures, or OS restarts.

In simple terms:
> **Committed data must never be lost.**

Durability is what gives databases their reliability in real-world systems.

---

## 1. What is Durability?

Durability ensures that:
> After a transaction commits successfully, all changes made by that transaction **will survive failures**.

Once the DBMS returns a **COMMIT success**, the user can trust that the data is safely stored.

---

## 2. Why Durability Is Necessary

Without durability:
- A committed bank transaction could disappear after a crash
- Data loss would occur after power failures
- Databases would be unreliable for real-world use

Durability is essential for:
- Financial systems
- E-commerce
- Reservation systems
- Any critical data-driven application

---

## 3. Durability with a Simple Example

### Bank Deposit Transaction
```sql
BEGIN;
UPDATE account SET balance = balance + 5000 WHERE acc_id = 'A';
COMMIT;
```

After `COMMIT`:

* Even if the system crashes immediately
* Even if power fails
* Even if OS restarts

👉 The balance **must remain updated** when the system recovers.

---

## 4. How DBMS Ensures Durability

Durability is implemented using **persistent storage** and **recovery mechanisms**.

---

### 4.1 Write-Ahead Logging (WAL)

> **Changes must be written to stable storage (log) before being committed.**

Steps:

1. Transaction modifies data in memory (buffer)
2. DBMS writes log records to disk
3. Log is flushed to disk
4. Only then is `COMMIT` acknowledged

Even if data pages are not yet written to disk, the **log is**.

---

### Log Record Example

```
<T1, A, old=10000, new=15000>
<T1, COMMIT>
```

This allows recovery to **redo committed transactions**.

---

### 4.2 REDO Logging

Durability primarily depends on **REDO operations**.

### REDO ensures:

* Committed changes are reapplied during recovery
* No committed data is lost after crash

During recovery:

* DBMS scans logs
* Reapplies all committed transactions

---

### 4.3 Stable Storage

Durability requires storage that survives failures:

Examples:

* Hard disks
* SSDs
* NVMe
* RAID systems

Memory (RAM) alone is **not durable**.

---

### 4.4 Checkpoints

A checkpoint is a point where:

* Dirty pages in memory are written to disk
* Log is synchronized

### Why Important?

* Reduces recovery time
* Limits how far DBMS must scan logs

Checkpoint does NOT replace logging; it optimizes durability.

---

## 5. Durability and Crash Recovery

When a crash occurs:

1. DBMS restarts
2. Reads the transaction log
3. Identifies committed transactions
4. **Redoes** their changes
5. Ignores uncommitted transactions

Thus:

* Committed → preserved
* Uncommitted → discarded

---

## 6. Durability vs Atomicity

| Aspect       | Atomicity                | Durability                    |
| ------------ | ------------------------ | ----------------------------- |
| Focus        | All-or-nothing execution | Persistence of committed data |
| Handles      | Partial failures         | System crashes                |
| Uses         | UNDO logging             | REDO logging                  |
| When applied | Before commit            | After commit                  |

Atomicity ensures **rollback**, durability ensures **persistence**.

---

## 7. Durability vs Isolation

| Aspect    | Durability           | Isolation             |
| --------- | -------------------- | --------------------- |
| Concern   | Data survival        | Concurrent visibility |
| Mechanism | Logging, disk writes | Locks, MVCC           |
| Timing    | After commit         | During execution      |

They solve completely different problems.

---

## 8. What Can Affect Durability?

### Reduced Durability Modes

Some DBs allow:

* Delayed log flushing
* Async commits

This improves performance but risks:

* Losing last few committed transactions on crash

Example:

```sql
SET synchronous_commit = OFF;
```

Used only when **performance > reliability**.

---

## 9. Common Misconceptions

### ❌ Wrong

> Durability means data is immediately written to disk.

### ✅ Correct

> Durability means data can be **recovered**, even if not immediately written to disk.

Logs ensure durability even with delayed data writes.

---

## 10. When Durability Can Be Relaxed

Durability may be relaxed in:

* Caching systems
* Analytics systems
* Temporary data
* Performance-critical systems with acceptable data loss

But never in financial or critical systems.

---

## Summary Table

| Aspect          | Durability                  |
| --------------- | --------------------------- |
| Ensures         | Committed data is permanent |
| Failure handled | Crashes, power loss         |
| Core mechanism  | Write-Ahead Logging         |
| Recovery action | REDO                        |
| Storage         | Disk / SSD / stable storage |
| Trade-off       | Performance vs reliability  |

---

## Key Takeaways

* Durability guarantees **no committed transaction is lost**.

* Implemented using **logging, stable storage, and recovery**.

* Relies mainly on **REDO operations**.

* Checkpoints improve recovery efficiency.

* Durability is critical for real-world reliable databases.
