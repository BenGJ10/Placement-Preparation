# Atomicity in ACID

**Atomicity** is the first and most fundamental property of ACID.  

It guarantees that a **transaction is treated as a single, indivisible unit of work**—either it completes entirely or it has **no effect at all** on the database.

If any part of a transaction fails, the **entire transaction is rolled back**.

---

## 1. What is Atomicity?

Atomicity ensures that:
**All operations of a transaction are executed successfully, or none of them are applied.**

There is **no partial execution** visible to the database.

In simple terms:
- **Success → COMMIT**
- **Failure → ROLLBACK**

---

## 2. Why Atomicity is necessary

Without atomicity, databases would easily enter **inconsistent states**, especially during:
- System crashes
- Power failures
- Application errors
- Constraint violations

Atomicity ensures that **incomplete transactions never corrupt data**.

---

## 3. Atomicity with a Real Example

### Bank Transfer Example

Transfer ₹1000 from Account A to Account B.

```sql
UPDATE accounts SET balance = balance - 1000 WHERE acc_id = 'A';
UPDATE accounts SET balance = balance + 1000 WHERE acc_id = 'B';
```

### Possible Scenarios

| Scenario                            | Result                        |
| ----------------------------------- | ----------------------------- |
| Both updates succeed                | Transaction commits           |
| First update succeeds, second fails | Entire transaction rolls back |
| System crashes mid-transaction      | Rollback on recovery          |

**Atomicity ensures money is never “lost” or “created”.**

---

## 4. Atomicity vs Partial Failure

Consider this transaction:

```sql
BEGIN;
INSERT INTO orders VALUES (101, 'Laptop');
INSERT INTO payments VALUES (101, 'SUCCESS');
COMMIT;
```

If the second `INSERT` fails:

* The first insert **must also be undone**
* Otherwise, an order exists without payment → **logical inconsistency**

Atomicity prevents this situation entirely.

---

## 5. How DBMS implements Atomicity

Atomicity is implemented using **logging and recovery mechanisms**, primarily:

---

### 5.1 Write-Ahead Logging (WAL)

**Core Rule:**

> Before modifying data on disk, the DBMS writes the change to a log.

The log contains:

* Transaction ID
* Old value (before change)
* New value (after change)

Example log entry:

```
<T1, AccountA, old_balance=5000, new_balance=4000>
```

This ensures the DBMS can:

* **Undo** changes if transaction fails
* **Redo** changes if system crashes after commit

---

### 5.2 Undo and Redo Operations

| Operation | Purpose                                     |
| --------- | ------------------------------------------- |
| **UNDO**  | Revert changes of incomplete transactions   |
| **REDO**  | Reapply committed changes lost due to crash |

Atomicity mainly relies on **UNDO**.

---

### 5.3 Rollback Mechanism

When a transaction fails:

* DBMS scans the log
* Reverses all changes made by that transaction
* Restores database to previous consistent state

```sql
ROLLBACK;
```

---

## 6. Atomicity and System Failures

### Types of Failures Atomicity Handles

| Failure Type         | Atomicity Role           |
| -------------------- | ------------------------ |
| Transaction failure  | Roll back transaction    |
| System crash         | Undo uncommitted changes |
| Power failure        | Restore from logs        |
| Constraint violation | Abort transaction        |

Atomicity **does not care why a failure occurred**—it only ensures **no partial effects remain**.

---

## 7. Atomicity vs Consistency

| Aspect         | Atomicity                  | Consistency                  |
| -------------- | -------------------------- | ---------------------------- |
| Focus          | All-or-nothing execution   | Valid state transitions      |
| Concerned with | Transaction execution      | Database rules & constraints |
| Example        | Both debit & credit happen | Balance never goes negative  |

Atomicity ensures **transaction completeness**, not correctness of logic.

---

## 8. Atomicity in Nested Transactions

In nested transactions:

* Inner transaction failure causes rollback of **only inner transaction**
* Outer transaction can still continue

Example:

```
T1
 ├─ T1.1 (fails → rolled back)
 └─ T1.2 (continues)
```

Final commit depends on the parent transaction.

---

## 9. Atomicity and Savepoints

Savepoints allow **partial rollback within a transaction**, but atomicity still holds at the transaction level.

```sql
BEGIN;
UPDATE account SET balance = balance - 500;
SAVEPOINT sp1;
UPDATE account SET balance = balance - 500;
ROLLBACK TO sp1;
COMMIT;
```

* One update is undone
* Transaction still commits atomically as a whole

---

## 10. What Atomicity does not guarantee

Atomicity does **not** guarantee:

* Isolation from other transactions
* Correctness of business logic
* Prevention of concurrency issues

These are handled by:

* **Isolation**
* **Consistency**
* **Concurrency control mechanisms**

| Aspect            | Atomicity                |
| ----------------- | ------------------------ |
| Ensures           | All-or-nothing execution |
| Failure Handling  | Rollback                 |
| Core Mechanism    | Logging + UNDO           |
| Prevents          | Partial updates          |
| Implemented using | WAL, transaction logs    |
| Works at          | Transaction level        |

---

## Key Takeaways

* Atomicity ensures **no partial effects** of a transaction are visible.

* Implemented using **write-ahead logging and rollback**.

* Handles crashes, errors, and failures safely.

* Does **not** ensure correctness—only completeness.

* Foundation for reliable transaction processing.
