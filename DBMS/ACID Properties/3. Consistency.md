# Consistency in ACID

**Consistency** is the ACID property that ensures a transaction transforms the database from **one valid state to another valid state**, preserving all **defined rules, constraints, and business logic**.

Unlike Atomicity and Isolation (which are largely enforced by the DBMS engine), **Consistency is a shared responsibility** between the **database system** and the **application logic**.

---

## 1. What is Consistency?

Consistency guarantees that:
> After a transaction commits, the database satisfies **all integrity constraints** and **business rules** defined on it.

If a transaction violates any rule, it **must not be committed**.

---

## 2. What Consistency Ensures

A consistent database state means:
- All **constraints** are satisfied
- All **relationships** are valid
- All **business invariants** hold true

### Examples of Consistent State
- Account balance is never negative
- Every foreign key references an existing primary key
- Unique values remain unique
- Domain rules (data types, ranges) are enforced

---

## 3. What Consistency Does NOT Mean 

Consistency **does NOT mean**:
- Data is correct according to real-world truth  
- Transactions are isolated  
- Transactions are atomic  

Those are covered by other ACID properties.

Consistency only means:
> **All rules defined by the schema and application are respected.**

---

## 4. Consistency with a Simple Example

### Bank Account Rule
**Invariant:** Total balance in the system must remain unchanged after transfer.

```sql
BEGIN;
UPDATE account SET balance = balance - 1000 WHERE id = 'A';
UPDATE account SET balance = balance + 1000 WHERE id = 'B';
COMMIT;
```

If either:

* Balance becomes negative
* Foreign key constraint fails
* Check constraint fails

→ Transaction must be **rolled back**.

---

## 5. Types of Consistency Constraints

Consistency is enforced through multiple layers of constraints.

---

### 5.1 Domain Constraints

Ensure values belong to a valid domain.

Examples:

* `age >= 0`
* `salary > 0`
* `gender IN ('M','F','O')`

Implemented using:

* Data types
* CHECK constraints

---

### 5.2 Entity Integrity Constraints

Ensure each entity is uniquely identifiable.

Rules:

* Primary key must be **unique**
* Primary key must be **NOT NULL**

Example:

```sql
PRIMARY KEY (student_id)
```

---

### 5.3 Referential Integrity Constraints

Ensure relationships between tables remain valid.

Rules:

* Foreign key must reference an existing primary key
* No orphan records allowed

Example:

```sql
FOREIGN KEY (order_id) REFERENCES orders(id)
```

---

### 5.4 User-Defined / Business Constraints

Application-specific rules.

Examples:

* Withdrawal amount ≤ account balance
* Order status transitions follow workflow
* Maximum credit limit not exceeded

Often enforced by:

* Triggers
* Stored procedures
* Application logic

---

## 6. Consistency vs Atomicity 
| Aspect         | Atomicity                | Consistency              |
| -------------- | ------------------------ | ------------------------ |
| Focus          | All-or-nothing execution | Valid state transitions  |
| Concerned with | Partial failures         | Rule violations          |
| Enforced by    | DBMS engine              | DBMS + application       |
| Example        | Rollback on crash        | Prevent negative balance |

A transaction can be:

* **Atomic but inconsistent** (bad logic)
* **Consistent only if logic + constraints are correct**

---

## 7. Consistency vs Isolation

| Aspect   | Consistency           | Isolation                       |
| -------- | --------------------- | ------------------------------- |
| Concern  | Database rules        | Visibility between transactions |
| Prevents | Constraint violations | Dirty / phantom reads           |
| Layer    | Schema & logic        | Concurrency control             |

Isolation protects consistency **during concurrency**, but they are **not the same**.

---

## 8. When Consistency is Checked

Consistency is checked:

* At **transaction commit time**
* After all statements execute
* Before making changes permanent

If any constraint fails:

* Transaction is aborted
* Database returns to previous consistent state

---

## 9. How DBMS Helps Maintain Consistency

The DBMS enforces:

* Constraints (PK, FK, UNIQUE, CHECK)
* Triggers
* Transaction rollback on violations

But **DBMS cannot guarantee correctness of business logic** unless explicitly defined.

---

## 10. Common Interview Misconceptions

### ❌ Wrong

> Consistency means database is always correct.

### ✅ Correct

> Consistency means database obeys **defined rules and constraints** after each committed transaction.

---

## 11. Practical Example of Inconsistency

```sql
BEGIN;
UPDATE employee SET salary = -5000 WHERE emp_id = 101;
COMMIT;
```

If CHECK constraint exists:

```sql
CHECK (salary > 0)
```

→ Transaction fails
→ Database remains consistent

Without constraint:
→ Atomic but **inconsistent**

## Summary Table

| Aspect           | Consistency           |
| ---------------- | --------------------- |
| Ensures          | Valid database states |
| Enforced by      | Constraints + logic   |
| Prevents         | Rule violations       |
| Checked at       | Commit time           |
| Depends on       | Correct schema design |
| Relation to ACID | Logical correctness   |

---

## Key Takeaways

* Consistency ensures **database rules are never violated**.

* It depends on **proper schema design** and **correct transaction logic**.

* DBMS enforces structural constraints; application enforces business rules.

* Atomicity and Isolation help preserve consistency, but do not define it.

* Poor constraints = atomic but inconsistent database.
