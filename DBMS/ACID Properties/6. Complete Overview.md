# ACID Properties – Complete Overview 
ACID properties define the **correctness guarantees** of database transactions.  

They ensure that a database remains **reliable, consistent, and fault-tolerant**, even under failures or concurrent access.

**ACID** stands for:
- **A**tomicity
- **C**onsistency
- **I**solation
- **D**urability

These properties apply to **transactions**, not individual SQL statements.

---

## 1. Atomicity

**Atomicity** guarantees that a transaction is treated as a **single, indivisible unit**:
> Either **all operations execute successfully**, or **none of them take effect**.

There is **no partial execution**.

---

### What Atomicity Prevents
- Partial updates
- Half-finished transactions
- Inconsistent intermediate states

### How It Is Achieved
- Rollback mechanisms
- Undo logging
- Transaction logs

---

## 2. Consistency

**Consistency** ensures that:
> A transaction transforms the database from **one valid state to another valid state**, obeying all rules and constraints.

These rules include:
- Primary key constraints
- Foreign key constraints
- CHECK constraints
- Business rules

### What Consistency Depends On
- Proper database schema design
- Correct transaction logic
- Constraint enforcement

The DBMS enforces structural rules; application logic enforces business rules.

---

## 3. Isolation

**Isolation** ensures that:
> Concurrent transactions do not interfere with each other.

Each transaction behaves **as if it were executed alone**, even when many transactions run simultaneously.

### Problems Isolation Prevents
- Dirty reads
- Non-repeatable reads
- Phantom reads

### How It Is Achieved
- Lock-based protocols
- Multiversion Concurrency Control (MVCC)
- Isolation levels (Read Committed, Repeatable Read, Serializable)

---

## 4. Durability

**Durability** guarantees that:
> Once a transaction commits, its changes are **permanently stored** and survive crashes or power failures.

### How It Is Achieved
- Write-Ahead Logging (WAL)
- Stable storage (disk/SSD)
- Redo logging
- Crash recovery mechanisms

---

## Online Bank Transfer Example

Let’s see **all four ACID properties together** using a single transaction.

## Scenario

Transfer **₹10,000** from **Account A** to **Account B**.

### Initial State
- Account A balance = ₹50,000
- Account B balance = ₹20,000

---

### Transaction Code

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 10000
WHERE acc_id = 'A';

UPDATE accounts
SET balance = balance + 10000
WHERE acc_id = 'B';

COMMIT;
```

---

## How Each ACID Property Applies

### 1. Atomicity in This Example

* If **both updates succeed** → transaction commits
* If **either update fails** (crash, constraint violation, error):

  * Entire transaction is rolled back
  * Account A is NOT debited
  * Account B is NOT credited

**Result:**
Money is never lost or partially transferred.

---

### 2. Consistency in This Example

Database rules:

* Balance cannot be negative
* Account IDs must exist
* Total money must remain constant

If:

* Account A has insufficient balance
* Account B does not exist
* CHECK constraint fails

→ Transaction is aborted
→ Database remains in a valid state

---

### 3. Isolation in This Example

Assume another transaction is checking balances at the same time.

Isolation guarantees:

* Other users cannot see Account A debited **without** Account B being credited
* No dirty reads
* No intermediate state is visible

Even with concurrent access:

* Each transaction sees a consistent snapshot

---

### 4. Durability in This Example

Once `COMMIT` succeeds:

* Even if the system crashes immediately
* Even if power fails
* Even if OS restarts

After recovery:

* Account A = ₹40,000
* Account B = ₹30,000

The transfer **cannot be lost**.

---

## ACID Properties Mapped to the Example

| Property        | What It Guarantees in the Example              |
| --------------- | ---------------------------------------------- |
| **Atomicity**   | Debit and credit happen together or not at all |
| **Consistency** | Balances remain valid and rules are preserved  |
| **Isolation**   | No other transaction sees partial transfer     |
| **Durability**  | Transfer persists after crashes                |

---

## ACID vs Non-ACID 

**Without ACID**:

* Partial transfers could occur
* Money could disappear or duplicate
* Concurrent users could see wrong balances
* Crashes could lose committed data

**With ACID**:

* Transactions are reliable
* Database integrity is preserved
* System behaves predictably

---

## Summary

| Property    | Core Idea               | Failure Handled        |
| ----------- | ----------------------- | ---------------------- |
| Atomicity   | All or nothing          | Partial execution      |
| Consistency | Valid state transitions | Rule violations        |
| Isolation   | No interference         | Concurrency anomalies  |
| Durability  | Permanent commit        | Crashes, power failure |

---

## Key Takeaways

* ACID properties work **together**, not independently.

* Atomicity and Durability rely heavily on **logging**.

* Consistency depends on **constraints + logic**.

* Isolation controls **concurrent visibility**.

* ACID is essential for **banking, finance, e-commerce, and critical systems**.
